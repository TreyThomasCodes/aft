## intent

Agents ignore AFT's code-health surfaces for fixture-checkable reasons. On the passive surface, the status bar shows stale counts with a `~` disclaimer, renders analyzer absence as `E0 W0`, and presents project-wide aggregates that are not tied to the current task. Retirement and replacement of that passive surface belong to the alert-channel-and-bar-retirement campaign. On the explicit surface owned here, `aft_inspect` can return cache-with-disclaimers such as `provisional` and `pending_categories`, can render missing diagnostics as zero — the absence-as-zero shape, whose warm-store instance is the `server_ran: false` payload emitted with zero counts by a server that never ran — and can present stale cached data as usable. This campaign removes those explicit-inspect behaviours; it does not remove the project-wide summary mode of a bare `aft_inspect`.

These are four observed surface behaviours, not five: passive-bar stale counts, passive-bar analyzer absence-as-zero, passive-bar project-wide aggregates, and explicit-inspect cache-with-disclaimers. This campaign removes only the explicit-inspect response behaviours — provisional or pending payloads, stale cached inspect data presented as usable, and missing diagnostics rendered as zero. The sibling alert-channel-and-bar-retirement campaign owns the passive-bar stale-count, passive-bar absence-as-zero, and passive-bar project-wide-aggregate behaviours. Behaviour-class names are not cross-surface ownership: inspect occurrences belong here and passive-bar occurrences belong to that sibling campaign.

This campaign makes explicit inspection authoritative while leaving passive notification design to the alert-channel-and-bar-retirement campaign. Wake-digest rendering, status-bar retirement, alert formatting, and their byte-goldens are outside this campaign. Inspect-side deferred delivery, the existing status-bar write encountered during that conversion, plugin copy, and the shared release boundary remain in scope here.

1. **Blocking-fresh inspect.** An explicit `aft_inspect` produces no progress frames and, whenever it terminates, exactly one terminal response — on NDJSON, on subc, and on MCP alike, including at daemon shutdown, where that terminal frame is emitted before the pending registry entry is dropped rather than being cleared away silently. A FRESH response contains data mechanically verified against the inspected tree for every category required by the current category contract, and carries no partial-result vocabulary at any depth. It never covers a verified subset while another required category is unverified. Until GATE-7a rules otherwise, every member of `InspectCategory::active()` is required and `sections=` changes drill-down detail only.

2. **Mechanical freshness.** Diagnostics require a version/epoch-valid result plus a completion proof over the obligated document set for every snapshotted applicable server kind. That snapshot is produced by side-effect-free applicability resolution before any process starts and binds for the call's whole life; applicability discovered mid-call applies to the next inspect, and an unavailable executable is never reclassified as inapplicable to make a cold inspect green. Rust-analyzer's quiescence signal is part of that kind's completion proof, not a substitute for it: every supported kind, rust-analyzer included, has its obligated set and mechanically observable completion boundary ruled by GATE-9. An EMPTY applicability snapshot does not satisfy this vacuously — a root with no applicable server is the no-applicable-analyzer terminal GATE-1 rules, and until that ruling lands it may render neither zero diagnostics nor any clean-state claim. Tier-2 requires either stat verification of persisted artifact identity or rebuild-completed-and-published after any required callgraph work, with the generation pointer swap observed. Todos and metrics are fresh only when computed in-call over the stat-verified file list. Wall-clock age, debounce, quiet time, cached prose, and the wait-stamp are not freshness evidence. Freshness is asserted PAYLOAD-SHAPED — field presence/absence and verified-count identity — never by `JobOutcome` variant, because `run_diagnostics_category` returns `JobOutcome::Fresh` unconditionally today. Inspect-triggered rebuild admission is an intent rather than a terminal-delivery guarantee: it should be prompt subject to the cold-build limiter and writer lease, while acceptance asserts only the specific scheduling claims constraints pin — the fixed 32-release deterministic-admission clause against the new admission-event surface, with the overtaking clause held at GATE-8.

3. **Auditable cost.** Every FRESH response carries a wait-stamp with human-readable cost text and an ordered completed-phase list. The logical phase-entry shape is `{id, producer?, category?, also_satisfied?: [category,...]}`; `also_satisfied` is present only for a physical work unit that freshened categories beyond its primary category, and consumers treat absence as empty. The closed IDs and attribution rules are defined in constraints. The list contains completed verification or work phases, not merely phases on which the caller blocked, and is derived from the server-side inspect-phase log rather than assembled independently. That log is a named internal artifact this campaign builds — explicitly not `run_tool_call::PhaseTrace` — with a stated harness read path, and recording it observes rather than alters publication. A warm stat-verified result therefore lists `stat_verification` while its text states that no blocking wait occurred. An empty list means no phase completed; it does not mean a warm hit.

4. **Explicit non-fresh outcomes.** Whenever inspect terminates without freshness, it returns INTERRUPTED or PHASE-FAILED and presents no category counts as current. INTERRUPTED is reserved exclusively for a user-message detach or abort; a verification failure is PHASE-FAILED, never INTERRUPTED. Both non-fresh terminals carry the SAME ordered completed-phase list and the same entry shape the wait-stamp uses — empty in the preflight form — with PHASE-FAILED additionally carrying `failed_phase`, `failure_reason`, optional `failure_detail`, and the `failed_phase` producer or category detail where that ID takes one; carrying that list is a cost record, not a counts channel. EVERY PHASE-FAILED CARRIES A REASON, including the preflight form, which drops phase attribution but not the cause: `failure_reason` is drawn from the closed per-phase enum pinned in interfaces — or from its preflight list — a reason valid for one phase is invalid on another, and `failure_detail` is prose that may never stand in for a missing or mismatched reason. PHASE-FAILED requires a mechanically observable failure (including a GATE-9 oracle-failure signal), daemon shutdown, or a GATE-1-ruled ceiling. Elapsed silence alone is not failure evidence. If no ceiling or mechanical signal exists, an unquiesced call may remain in phase until interruption or shutdown; the closed terminal taxonomy is not an unconditional liveness guarantee.

5. **Scope semantics.** `scope=` narrows results. Until GATE-2 rules a narrowed applicable-server snapshot, it does not reduce server starts, obligated documents, or freshness work. `sections=` narrows detail, not the required category set. No deadline-truncated scoped result is permitted.

6. **Truncation is retired, not relabelled.** No elapsed budget of any kind may convert unfinished work into a returnable result — not FRESH, not Pending, not Stale, not cached-as-current, not provisional, not a verified subset. Both retired budget families leave the blocking path together: the Tier-2 wait budget with its carriers and environment overrides, and the diagnostics deadline. Retiring one while leaving the other standing ships deadline-truncated diagnostics under a FRESH label and is the most likely way to pass this campaign while violating it. A failure ceiling, if GATE-1 rules one, is failure policy whose only legal expiry effect is whole-call PHASE-FAILED with no current-result payload; it is never freshness evidence and never permission to restore a retired conversion site.

7. **The cost model inverts, deliberately.** Today an unscoped inspect is the cheap warm read and only the scoped path opens files and waits. Under fresh-only, diagnostics is always active, so a bare unscoped `aft_inspect` starts every server in the applicability snapshot and becomes the MOST expensive call — and, because the snapshot ignores `scope` until GATE-2 rules otherwise, so does a scoped one. That cost is accepted rather than mitigated by a knob: this campaign adds no freshness opt-out, no allow-stale, and no caller-settable deadline, budget, or ceiling. The bound on it is structural — at most one process per (root, applicable server kind), which a per-root single-process cap could not satisfy on a mixed-language root without leaving one language permanently unverifiable, and no start outside the snapshotted set. Starts occur only on explicit inspect and drill-down requests, never on the passive or `health.digest` path, and started servers are tracked and idle-reaped; the cautionary bound is unreaped orphans, not a per-root process cap.

## design

The design preserves a single authoritative response path: `handle_inspect` registers one deferred response, background work resolves the side-effect-free applicability snapshot, completes LSP and Tier-2 verification, derives the shared completed-phase list from the inspect-phase log, and delivers exactly one FRESH, INTERRUPTED, or PHASE-FAILED terminal. FRESH alone carries the wait-stamp; non-fresh terminals carry the same ordered entries, with PHASE-FAILED additionally carrying its pinned failure fields and attribution.

The logical phase-entry shape is `{id, producer?, category?, also_satisfied?: [category,...]}`. `also_satisfied` records extra categories freshened by one physical work unit and is absent otherwise; consumers treat absence as an empty list. Literal field spellings remain GATE-1d, while `failed_phase`, `failure_reason`, and optional prose `failure_detail` remain pinned now.

Implementation follows the non-overlapping slice partition in constraints. In particular, deferred `handle_inspect` conversion and lock-released LSP start/wait work are one inspect-path slice; freshness emitters, limiter admission, and plugin/tool descriptions land through their distinct seams.

## constraints

- **Honest reporting.** "Fresh" claims must be mechanically true. The verification tickets are: document version or epoch match, the server-kind diagnostics completion oracle (GATE-9) including rust-analyzer quiescence where that server applies, stat-verified artifact identity, rebuild-completed-and-published (generation pointer swap observed), and, for todos and metrics, an in-call computation over the stat-verified file list. Wall-clock age and wait-stamp text are NOT freshness evidence. The protocol.rs tri-state convention (`success` + `complete` + named gap fields) remains the honesty convention for commands that are ALLOWED to be partial. Blocking `aft_inspect` is EXPLICITLY EXEMPT: it does not use partial-success at all. Stated without an or-clause so FRESH cannot swallow its own negation: a FRESH terminal inspect response carries mechanically verified data for EVERY requested category, plus the wait-stamp; if any requested category cannot be verified, the call is not FRESH — a verification failure is PHASE-FAILED; INTERRUPTED is reserved exclusively for a user-message detach or abort. A FRESH response contains, RECURSIVELY — meaning at ANY depth of the emitted payload, with top level, `scanner_state`, `summary`, and `details` named as the MINIMUM containers an assertion must walk rather than as the exhaustive list, so a check of the named sites alone cannot go green while a banned field ships one level deeper — none of `provisional`, `provisional_counts`, `pending_categories`, `stale_categories`, `incomplete_categories`, `scope_truncated`, `servers_pending`, `servers_not_installed`, `files_without_server`, any `server_ran: false` payload, `failed_categories`, `complete` in any valuation, the `stale` sentinel in any valuation, per-category `status: pending|stale|failed` sentinels, or stale-with-counts. `incomplete_categories` is named explicitly because `build_inspect_payload` emits it UNCONDITIONALLY under `scanner_state`, so a generic ban plus a named-field assertion that omits it goes green while the field ships; `server_ran: false` is named for the same reason on the diagnostics side, since `collect_warm_working_set` / `DiagnosticsCollection::into_payload` emit it as the absence-as-zero shape. The ban is on partial-result FIELDS generally, not on those names.

- **The FRESH payload has a positive shape, not only prohibitions.** Specified by prohibition alone, no consumer and no golden can be written. Pinned NOW at the logical level, with exact wire spelling deferred to GATE-1d: a FRESH response carries a wait-stamp with (i) a human-readable text field and (ii) an ORDERED `phases` array whose entries are records `{id, producer?, category?, also_satisfied?: [category,...]}`. `id` is a member of the closed phase-ID set below and an unknown ID is a failure. `producer` is the stable server identifier; it is PRESENT ON EVERY `lsp_start` AND `lsp_quiescence` ENTRY — including on a single-server root, so goldens and consumers never branch on server count — and ABSENT on `callgraph_ready`, `tier2_rescan`, `stat_verification`. `category` is the canonical `InspectCategory` wire name; it is PRESENT on `callgraph_ready`, `tier2_rescan`, and `stat_verification` entries, which are per-category work, and ABSENT on the two LSP entries. Neither attribution dimension may be encoded by minting a new phase ID. `also_satisfied` is PRESENT iff one physical unit of work freshened additional categories beyond the entry's primary `category` (the shared-callgraph case), and is ABSENT otherwise; consumers MUST treat absence as an empty list.
  THE ARRAY IS THE COMPLETED-PHASE LIST, NOT A BLOCKED-ON LIST, stated so it cannot contradict the warm arm: it contains every verification or work phase whose completion the inspect-phase log recorded for the call, whether or not the caller blocked on it. A warm call whose Tier-2 categories were proved current by stat-verification therefore lists a `stat_verification` entry per verified category and the canonical formatter renders `waited: no`; an EMPTY `phases` array means no phase completed at all, and a stamp is never omitted. Repeated bare IDs with no `category` attribution are forbidden, because one inspect runs several Tier-2 categories and may verify, build, or rescan more than once, and PHASE-FAILED must be able to name which category's phase failed. If one physical callgraph build satisfies several categories, the log records the admitting category once and `also_satisfied` as the ordered, duplicate-free additional categories; the field is absent when no additional category was freshened, and duplicating the build as multiple executions is a failure. Array order is completion-log order; concurrent phases need not have a deterministic cross-phase order, but each entry remains attributable and per-category ordering (`callgraph_ready` before that category's `tier2_rescan`) is preserved.
  THE ENTRY SHAPE IS SHARED ACROSS ALL THREE TERMINALS, so a consumer parses one shape rather than one per outcome: FRESH carries the wait-stamp (human text plus the ordered array); (b) INTERRUPTED and (c) PHASE-FAILED carry the same ordered completed-phase list, built from the same entry records under the same attribution rules, and (c) additionally carries `failed_phase`, `failure_reason` — drawn from the CLOSED per-phase enum pinned in interfaces, which GATE-1d does not reopen — optional prose `failure_detail` that may not mint another reason, and the `failed_phase` attribution detail where that ID takes one. The preflight form is exactly that list EMPTY with `failed_phase` OMITTED; it still carries an applicable preflight `failure_reason` and optional `failure_detail`, because the form drops phase attribution, not the reason. Carrying the list on a non-fresh terminal is NOT a counts channel: the (b)/(c) prohibition on numeric category counts, category summary objects, and any details payload readable as a current result is unaffected by it, and a completed-phase entry may never be rendered as a per-category result.
  GATE-1d additionally rules: the wire field names for the stamp, its entries, and the `category`/`producer`/`also_satisfied` detail fields; the taxonomy label field name and spelling; and — by ENUMERATION, not by residue — which of today's `scanner_state` keys survive the field ban (`tier2_last_run`, `tier2_trigger_reason`, `disabled_categories` are unaccounted for after the banned keys are removed). Acceptance asserts the surviving key set POSITIVELY as well as by absence. GATE-1d does NOT reopen the PHASE-FAILED field names `failed_phase` / `failure_reason` / `failure_detail` or the closed per-phase `failure_reason` enum; those are pinned in interfaces and change only by recorded amendment there.

- **Canonical wait-text formatter.** The logical human-text value is rendered only by one canonical formatter from two inputs: the ordered completed-phase list and the recorded `blocking_waited` boolean. Its grammar is exactly `waited: <yes|no>; completed: <id[,id...]|none>` in completion-log order. Thus a stat-verified warm hit with completed entries has `waited: no`, while a cold call that blocked has `waited: yes`; an empty list renders `completed: none` and never means warm. Fixture goldens assert this logical value after GATE-1d fixes the containing wire field name; until then no literal-field-name golden is committed. No consumer parses the display text as freshness evidence.

- **Named emitters, BOTH SIDES — the Tier-2 list alone does not cover diagnostics.** Tier-2/aggregate emitters of banned fields: `summary_for` / `status_summary` / `computed_summary_for` (the stale-with-cached-payload branch inserting the `stale: true` sentinel while keeping counts) and `build_inspect_payload` (which also emits `incomplete_categories`). SEPARATELY NAMED, because they are a different code path and a different failure: the diagnostics-side emitters are `diagnostics_summary_for` (the incomplete/pending branch emitting `provisional_counts`, `status`, `servers_pending`, `servers_not_installed`, `files_without_server` while zeroing top-level counts) and `collect_warm_working_set` / `DiagnosticsCollection::into_payload` (the warm-store read producing `server_ran: false` with zero diagnostics — the absence-as-zero shape intent names). FRESH must take none of these branches. CRITICAL FOR TEST DESIGN: `run_diagnostics_category` today returns `JobOutcome::Fresh { payload }` UNCONDITIONALLY — its honesty lives inside the payload, not in the outcome variant. Therefore every freshness assertion in this campaign is PAYLOAD-SHAPED (field presence/absence and verified-count identity), never `JobOutcome`-variant-shaped; a variant-only assertion passes vacuously on the diagnostics path and proves nothing.

- **The existing inspect deadline machinery is RETIRED, not relabelled (named conversion sites, BOTH deadline families) — and retirement is distinguished from a ruled failure ceiling.** Today `handle_inspect` bounds Tier-2 with `direct_tier2_wait_budget` plus `receive_direct_tier2` against an `Instant` deadline, treats `JobOutcome::Pending` / `JobOutcome::Stale` as a returnable result, and compensates afterwards with `ctx.request_tier2_refresh_pull()` and the `pending_tier2_paths` / `force_paths_completed` bookkeeping; the deadline also travels through `tier2_run_with_reuse_direct` / `wait_for_tier2_reuse_until`. THE DIAGNOSTICS DEADLINE IS RETIRED TOO AND IS NAMED SEPARATELY: `INSPECT_DIAGNOSTICS_DEADLINE`, `collect_scoped_diagnostics` / `collect_scoped_diagnostics_until`, and the `deadline` parameter of `LspManager::wait_for_file_diagnostics` on this path. The retirement also covers every environment or debug override of those conversion sites, including `AFT_INSPECT_DIRECT_TIER2_DEADLINE`, `AFT_INSPECT_DIRECT_TIER2_DEADLINE_ROOT`, and `AFT_INSPECT_DIRECT_TIER2_DEADLINE_MS`. Retiring only the Tier-2 budget while leaving the diagnostics budget standing ships deadline-truncated diagnostics under a FRESH label and is the single most likely way to pass this spec while violating it. THE RULE, STATED SO IT DOES NOT COLLIDE WITH GATE-1: no elapsed budget of any kind may CONVERT unfinished work into a returnable result — not FRESH, not Pending, not Stale, not cached-as-current, not provisional, not a verified subset. GATE-1 may still rule a transport-wide or per-phase FAILURE CEILING; such a ceiling is failure policy, not freshness evidence, its only legal expiry effect is whole-call (c) PHASE-FAILED carrying the in-flight `failed_phase` — or the preflight form when no phase has begun — the transport-level `failure_ceiling` reason from the closed enum, and optional `failure_detail` with no current-result payload, and it is not permission to restore any retired conversion site. Until GATE-1 lands no numeric ceiling and no `transportTimeoutMs` value is committed in a golden. Whether the pending-paths bookkeeping survives for the background lane is an implementation choice; it may NOT be the mechanism by which a non-fresh category becomes part of a returned FRESH payload. Also named: the `ctx.inspect_writer()`-false branch, which today falls back to `tier2_read_cached_readonly`. A reader-only daemon may serve Tier-2 ONLY where stat-verification proves the persisted artifact matches the current tree; if a rebuild is required and this process cannot take the writer lease, the call is (c) PHASE-FAILED, never readonly cached output presented as current. THAT TERMINAL IS ATTRIBUTED RATHER THAN LEFT UNNAMEABLE, because the closed per-phase enum does not cover every lease case: where the required rebuild includes a callgraph build, the terminal is `failed_phase: callgraph_ready` with `failure_reason: writer_lease_unavailable`; where the required work is a Tier-2 rescan needing NO callgraph, the enum interfaces pins today admits no lease reason for `tier2_rescan`, so the terminal is `failed_phase: tier2_rescan` with `failure_reason: writer_lease_unavailable`; any `failure_detail` remains optional free prose and is never the operative cause, and minting a distinct `tier2_rescan` lease reason is a recorded amendment to interfaces rather than an implementation choice. In neither case may the lease failure be rendered as preflight, as a stale read, or as a FRESH subset.

- **The category set is FIXED and not caller-selectable — "requested category" is defined here (GATE-7a).** `handle_inspect` parses only `sections`, `scope`, and `topK`, then iterates `InspectCategory::active()` unconditionally; `sections` selects DRILL-DOWN DETAIL, not which categories run. So "requested category" means EVERY member of `InspectCategory::active()`, and the whole-call-failure default has a consequence recorded rather than discovered: one unfreshable Tier-2 category fails a call whose todos, metrics, and diagnostics were all verified. No implementation may narrow the obligation by reinterpreting `sections` as a category selector. Whether a real selector is introduced, and whether it changes that blast radius, is GATE-7a; until it lands the all-active reading binds.

- **Tier-1 freshness and non-resolution pre-phase refusals (GATE-7b).** Todos and metrics are FRESH iff each is computed in-call over the stat-verified file list; that in-call computation is their verification ticket. They still dispatch through `manager.submit_category_with_callgraph`, whose non-fresh outcomes may not appear inside a FRESH payload. The unresolved issue is phase attribution and the rendering of non-resolution refusals: `heavy_root_work_allowed()` false (`JobOutcome::Failed` with the heavy-root-work block message), `cache_for_snapshot` / `InspectCache::open_readonly` failure, and `validate_tier2_read_category` rejection. Because the taxonomy is a CLOSED set of three and the closed phase-ID set contains no Tier-1 computation ID, a Tier-1 computation failure or one of those refusals terminates as (c) PHASE-FAILED IN THE PREFLIGHT FORM (empty completed-phase list, no `failed_phase`, no counts, no clean-state claim), carrying the applicable preflight `failure_reason` from the closed enum pinned in interfaces — `heavy_root_work_blocked`, `cache_open_failed`, `category_validation_rejected`, or `tier1_compute_failed` — plus optional `failure_detail`, unless a recorded GATE-7b amendment supplies phase attribution or a distinct refusal shape.

- **Diagnostics COMPLETENESS, not just per-document verification (GATE-9).** A version/epoch-verified publish proves freshness for a document; it does not prove the server has reported every diagnostics-bearing document in the obligated set. Without a per-server-kind completion oracle, a push-based server that has reported one file yields a zero-count FRESH — reintroducing absence-as-zero. The supported-kind set is derived from the shipped LSP registry plus configuration table, and each acceptance fixture enumerates that derived set in test. Therefore each derived server kind must have a recorded obligated document/workspace set and a mechanically observable completion boundary before FRESH diagnostics ship; elapsed quiet time is not such a boundary unless GATE-1 rules it a failure ceiling rather than freshness evidence. A zero-diagnostics result is FRESH only once every snapshotted applicable server has produced its completion proof over the full obligated set. VACUITY IS CLOSED, so this rule cannot be satisfied by having nothing to prove: an EMPTY applicability snapshot (no applicable server for the root) does NOT satisfy it vacuously — that case is the no-applicable-analyzer terminal ruled by GATE-1, and until GATE-1 lands it may render neither zero diagnostics nor any clean-state claim, exactly as the applicable-server-set constraint states. CONSEQUENCE FOR ACCEPTANCE: a single accepted publish never completes `lsp_quiescence` for a kind whose obligated set has more than one member, and EVERY arm whose terminal is a FRESH diagnostics result carries the GATE-9 label or is split so only its prohibitions run now.

- **Single terminal inspect response (RULED), and the inspect-phase log is a NAMED artifact with a read path.** No deferred partial updates, no progress frames, no new NDJSON push machinery. The terminal wait-stamp is the only agent-visible cost report and lists only phases that actually ran. Phase start/completion/duration/terminal-error are written server-side to the INSPECT-PHASE LOG. That log is NOT `run_tool_call::PhaseTrace`, which is a fixed-field subc dispatch-milestone recorder (`frame_decoded`, `executor_submitted`, `job_admitted`, `translate_done`, `execute_done`, `format_done`, `finalize_done`) with no inspect phase IDs, producer keys, or terminal-error field; building it is REQUIRED WORK, not reuse, and the identical phase-boundary code runs on every transport. BECAUSE FIVE ACCEPTANCE ARMS READ IT, ITS SHAPE IS PINNED HERE RATHER THAN LEFT TO THE IMPLEMENTER: records are per-inspect-call and correlated by request id; each record carries phase id, the producer key where the ID takes one, the category where the ID takes one, start/completion, duration, and terminal error; ordering within a call is guaranteed and is the order the completed-phase list is derived from; records are retained at least for the life of the call plus the assertion window; and the harness reads them through an in-process accessor as well as structured emission, so parity and "no LSP process started" assertions are readable without scraping prose. The log is INTERNAL AND HARNESS-FACING: it is not agent-visible output, so recording it does not create the push channel non_goals bans, and it is not a configuration knob. The earlier alias instructing readers that arms saying "PhaseTrace" mean this log is DELETED, so the wrong recorder cannot be reintroduced by name.

- **RETIRED ON THE INSPECT PATH — an index of the sites named above, adding no new rule.** The `direct_tier2_wait_budget` / `receive_direct_tier2` truncation and its `tier2_run_with_reuse_direct` / `wait_for_tier2_reuse_until` carriers, the `INSPECT_DIAGNOSTICS_DEADLINE` / `collect_scoped_diagnostics_until` truncation, `AFT_INSPECT_DIRECT_TIER2_DEADLINE`, `AFT_INSPECT_DIRECT_TIER2_DEADLINE_ROOT`, and `AFT_INSPECT_DIRECT_TIER2_DEADLINE_MS`, any return of `JobOutcome::Pending` / `Stale` from a blocking inspect, and the readonly-cached Tier-2 fallback except where stat-verified. Where this index and the retirement bullet above appear to differ, the retirement bullet governs.

- **Phase ID vocabulary is closed, shared, and semantically fixed.** `lsp_start`, `lsp_quiescence`, `tier2_rescan`, `callgraph_ready`, `stat_verification` are the ONLY machine-readable phase IDs. PREFLIGHT (the activity window) is everything before any phase: root resolution, applicable-set resolution, missing-executable discovery at resolution, and construction of the applicability snapshot. THE PREFLIGHT FORM (the terminal shape) is: (c) PHASE-FAILED with an empty completed-phase list, no `failed_phase`, no numeric counts, no category summary objects, and no clean-state claim; it DOES carry an applicable preflight `failure_reason` from the closed enum pinned in interfaces plus optional `failure_detail`, because the form omits phase attribution, not the reason. Preflight failures take the preflight form; so, under the interim GATE-7b rule, do post-preflight refusals and Tier-1 failures that can name no phase — the form is structural and is NOT an assertion that the failure occurred during preflight. `lsp_start` begins only AFTER a successful snapshot and covers process spawn through readiness for a record already in that snapshot — it does NOT cover applicable-set resolution; a spawn-time failure for a snapshotted server is `lsp_start` PHASE-FAILED, not preflight. `lsp_quiescence` covers acceptance of a version/epoch-verified diagnostics snapshot PLUS the server-kind completion oracle (GATE-9), and where the server is rust-analyzer its quiescence signal — a tsserver publish therefore also completes `lsp_quiescence` only once that kind's oracle is satisfied over its whole obligated set, because the ID names the verification step, not the rust-analyzer mechanism. `callgraph_ready` covers cold-build admission (phase start is the start of limiter wait), writer-lease acquisition, callgraph construction, and publication, and appears only where the requested Tier-2 work requires a callgraph. `tier2_rescan` covers Tier-2 computation and publication after any required callgraph is ready, and may complete with no `callgraph_ready` entry where none was required. `stat_verification` covers persisted-artifact identity verification with no rebuild, INCLUDING the gitignore-aware project-file walk that detects added/removed files — that walk is inside this ID's boundary, not a separate ID. THE PHASE IS RECORDED BY WHETHER THE CHECK RAN, NOT BY ITS VERDICT, stated so a mismatch is neither a silent omission nor a manufactured failure: where a persisted artifact exists and the check runs, `stat_verification` completes and is recorded for that category whether the artifact matched the tree or not; a NEGATIVE verdict is a completed `stat_verification` entry followed by that category's `tier2_rescan` (and its `callgraph_ready` where one is required), and is NOT `stat_verification_failed`, which names an inability to perform the check at all — a stat or project-walk error. Where no persisted artifact exists for a category, the check does not run and no `stat_verification` entry is minted for it. DETAIL DIMENSIONS, NOT NEW IDS: producer keys attach to `lsp_start` and `lsp_quiescence` ONLY and to EVERY entry carrying those IDs, including on a single-server root, so a mixed-language failure attributes to a server rather than to the root; the `category` dimension attaches to `callgraph_ready`, `tier2_rescan`, and `stat_verification` ONLY, so a repeated or failed Tier-2 phase attributes to a category rather than to the call. Producer keys may not be attached to the three project-scoped IDs, categories may not be attached to the two LSP IDs, and encoding either dimension by minting a per-server or per-category phase ID is banned. Each ID admits only the `failure_reason` values interfaces permits for it; a reason valid for one phase is not valid for another, and `failure_detail` adds prose only. Daemon shutdown names the in-flight phase (with its detail dimension where one applies) where one exists and otherwise takes the preflight form. Completed-phase lists contain only phases whose completion the inspect-phase log recorded. Human wait-stamp prose may paraphrase; the machine field may not. Adding an ID, moving a boundary, or rendering a preflight failure as a phase is a recorded amendment, not an implementation choice.

- **Stat-verification verdict semantics.** A completed `stat_verification` entry proves only that the identity check ran. ### Slice partitioning

The deferred-response conversion of `handle_inspect` and the on-demand LSP start/wait machinery MUST land as ONE inspect-path slice. They share the `handle_inspect` and `lsp/manager` files, and the pipeline rejects overlapping fences; splitting one change across competing slices would make either fence overlap or leave a half-converted path.

Natural non-overlapping slice seams are:

- **Inspect-path slice:** owns the `handle_inspect`/deferred-response conversion together with the lock-released LSP start and wait seam in `lsp/manager`, including phase-log derivation and transport handoff needed by that single path.
- **Limiter/admission slice:** owns `ColdBuildLimiter` admission classes, cancellation-aware acquisition, and harness-visible admission events; it does not edit the inspect-path or LSP-manager fence.
- **Scanner-freshness slice:** owns aggregate and diagnostics payload emitters, stat-verification/rebuild verdicts, and fresh-only field retirement; it does not edit deferred-response, limiter, or plugin fences.
- **Plugin/tool-description slice:** owns the pi and opencode terminal-shape consumers, tool descriptions, pending-follow-up retirement, prefix-cache bust, and release-manifest entry; it does not edit core inspect, LSP-manager, limiter, or scanner fences.

A graph minter must assign each shared file to exactly one of these slices. Cross-slice integration is by the interfaces and acceptance contracts above, not by overlapping file fences.

## non_goals

- **Fenced ground.** This campaign may add inspection-started idle-reap deadlines and shutdown escalation through existing child-registry/manager surfaces. It may not alter epoch, generation, or publication machinery, including their predicates, ordering, or visibility timing; it may not alter quiescence semantics. Additive obligated-set/completion tracking and inspect-phase-log recording remain allowed because they observe rather than alter publication.

- **No push, progress, or streaming channel.** Blocking inspect emits no intermediate frames, no progress or heartbeat events, and no deferred partial updates, and this campaign adds no new NDJSON push machinery, no new agent-visible event type, and no polling protocol for callers to re-ask about pending work. The single terminal response is the whole agent-visible surface. The inspect-phase log is internal and harness-facing and therefore does NOT create such a channel; converting it, or any part of it, into agent-visible output is out of scope and would be a recorded amendment.

- **No new global knobs.** This campaign introduces no user-visible or globally tunable configuration: no freshness opt-out, no "allow stale", no caller-settable deadline, budget, or ceiling, no per-call limiter tuning, and no environment override replacing a retired deadline-conversion site. Lifecycle constants (GATE-6) are fixed release constants, not knobs. This ban does NOT reach internal, harness-facing state that constraints and interfaces require: the inspect-phase log, the limiter admission event, and the internal per-request class/order state ticketed ordering would need are not knobs and may not be refused as such.

- **No caller-facing category selector is invented here.** `sections=` remains drill-down detail and `scope=` remains result narrowing. Whether a real selector exists, and whether it changes the whole-call blast radius, is GATE-7a; whether `scope=` narrows the applicability snapshot is GATE-2. Neither may be settled as an implementation choice inside this campaign.

- **Passive surfaces are not owned here.** Status-bar retirement, the agent alert block, the human fleet line, wake-digest rendering, alert formatting, alert-line length and truncation, and all of their byte-goldens belong to the alert-channel-and-bar-retirement campaign. This campaign touches the passive surface only where the deferred conversion forces it: the existing `refresh_status_bar_counts` write in `handle_inspect`, whose fate on this release boundary is GATE-10. `health.digest` copy is likewise out of scope beyond the manifest assertion that it introduces no agent tool-description change.

- **The fresh-Tier-2 / delta-engine consumer is not built here.** That boundary is a declared future interface minted by the alert-and-bar campaign; this draft specifies no implementation, no wire shape, and no acceptance contract for the handoff.

- **No real-repo performance claim.** The 5,000 ms warm bound is asserted against the canonical acceptance fixture's tree size only; no warm, cold, or per-repository latency guarantee is made for real repositories, and changing that number is a recorded amendment rather than a tuning exercise. Whether the warm-path stat-verification cost — per-record stat checks plus a gitignore-aware project-file walk per Tier-2 category — needs a ceiling of its own is REFERRED TO GATE-1 and is not answered here; if one is ruled it is failure policy under the whole-call rule and may not convert an unverified artifact into a returnable result.

- **Termination is not guaranteed by the taxonomy.** The closed set of three is an exhaustiveness rule about how a call ENDS, not a liveness promise that every call ends. Absent a GATE-1 ceiling or another mechanically observable failure signal, an unquiesced call may remain in phase until a user detach, an abort, or daemon shutdown supplies the terminal outcome. Supplying a liveness guarantee by having an implementation pick its own timeout is banned, not deferred.

- **The background and passive lanes are not rewritten.** Retiring the blocking path's deadline-conversion sites does not retire background warmup, maintenance builds, or the pending-paths bookkeeping where it serves the background lane; whether that bookkeeping survives there is an implementation choice, bounded only by the rule that it may never be the mechanism by which a non-fresh category enters a returned FRESH payload. `run_tool_call::PhaseTrace` is likewise untouched: this campaign neither extends it nor reuses it for inspect phases.

## glossary

- **Retired numeric bar:** the passive status-bar display that can show stale `~` counts or absence-as-zero. Its retirement and replacement belong to the alert-channel-and-bar-retirement campaign, not this one.
- **Agent alert block:** the agent-facing alert-channel rendering owned by the alert-channel-and-bar-retirement campaign. This campaign supplies inspect freshness semantics but does not define that rendering, its length, or its byte goldens.
- **Human fleet line:** the human-facing fleet/status presentation owned by the same alert-and-bar campaign. It is not an inspect terminal payload and must not be used as freshness evidence.
- **Wait-stamp:** the agent-visible cost report: human-readable text plus the ordered completed-phase list. It reports completed work; it is not freshness evidence. A FRESH terminal alone carries the wait-stamp; INTERRUPTED carries the ordered completed-phase list without the wait-stamp human text, and PHASE-FAILED carries that same list plus its pinned failure fields and attribution where applicable.
- **Phase entry:** one completed-work record in the wait-stamp, logically `{id, producer?, category?, also_satisfied?: [category,...]}`. `also_satisfied` is present only for a physical work unit that freshened categories beyond its primary category; consumers read absence as an empty list. The same entry shape is carried by all three terminals, so a consumer parses one shape rather than one per outcome.
- **Producer / category attribution:** the two detail dimensions carried by phase entries. `producer` is the stable server identifier and attaches to every `lsp_start` and `lsp_quiescence` entry, including on a single-server root. `category` is the canonical `InspectCategory` wire name and attaches to every `callgraph_ready`, `tier2_rescan`, and `stat_verification` entry. Neither dimension may be encoded by minting a new phase ID; the exact wire spellings are GATE-1d.
- **Closed phase-ID set:** `lsp_start`, `lsp_quiescence`, `tier2_rescan`, `callgraph_ready`, `stat_verification` — the only machine-readable phase IDs. An unknown ID is a failure, and adding an ID or moving an activity across an ID boundary is a recorded amendment rather than an implementation choice. Constraints fix each ID's activity boundary; this entry names the set only.
- **Recorded amendment:** a written change to this spec — in constraints, acceptance, or open_questions — that supersedes a pinned rule, constant, closed set, or gated arm. It is the only legal way to add a phase ID, move an ID boundary, add a fourth taxonomy label, add a `failure_reason` value or admit an existing one for a phase interfaces does not list it under, change the fixed 32-release admission schedule or the 5,000 ms warm bound, replace a GATE-7b interim rendering, or drop a gated arm. An implementation choice, a silent scope trim, or a diff that merely stops exercising an arm is not an amendment.
- **Verification ticket:** one of the enumerated mechanical proofs that may license a FRESH claim — document version or epoch match, the per-kind diagnostics completion oracle, stat-verified persisted-artifact identity, rebuild-completed-and-published (generation pointer swap observed), and, for todos and metrics, an in-call computation over the stat-verified file list. Wall-clock age, debounce, quiet time, cached prose, and wait-stamp text are not tickets. A non-fresh Tier-1 outcome takes PHASE-FAILED without entering a FRESH payload.
- **Payload-shaped assertion:** the required form of every freshness assertion in this campaign — field presence/absence and verified-count identity in the emitted payload, checked RECURSIVELY at any depth, with top level, `scanner_state`, `summary`, and `details` as minimum containers rather than an exhaustive traversal — never a `JobOutcome`-variant assertion and never a string match on human prose. `run_diagnostics_category` returns `JobOutcome::Fresh` unconditionally today, so a variant-only assertion passes vacuously on the diagnostics path and proves nothing.
- **Tier-1 / Tier-2 categories:** "tier" names the freshness path, not a display grouping. Tier-1 categories (todos, metrics) are FRESH iff each is computed in-call over the stat-verified file list; that computation is their verification ticket. Tier-2 categories are the persisted-artifact categories whose freshness is proved either by stat verification of artifact identity against the tree or by rebuild-and-publish after any required callgraph work, with the generation pointer swap observed. Both remain members of `InspectCategory::active()` and are equally required for FRESH until GATE-7a rules otherwise.
- **Whole-call-failure default:** the standing rule, in force until GATE-7a rules otherwise, that any single required category which cannot be mechanically verified fails the ENTIRE call as (c) PHASE-FAILED — even when every other category was verified. FRESH may never cover a verified subset, and an unavailable category may not be encoded inside a FRESH payload.
- **Failure ceiling:** a failure policy GATE-1 may rule — transport-wide or per-phase — whose ONLY legal expiry effect is whole-call (c) PHASE-FAILED carrying the in-flight `failed_phase`, or the preflight form when no phase has begun, with the transport-level `failure_ceiling` reason from the closed enum and optional `failure_detail`, with no current-result payload. A ceiling is never freshness evidence, never a licence to restore a retired deadline-conversion site, and no numeric ceiling or `transportTimeoutMs` value exists in a golden until GATE-1 lands. Absent such a ruling, elapsed silence leaves the call in phase rather than becoming PHASE-FAILED.
- **Failure reason / failure detail:** `failure_reason` is the machine-readable snake_case cause carried by every PHASE-FAILED terminal, drawn from the CLOSED per-phase enum pinned in interfaces — including the preflight list used by the preflight form. It is per-phase, so a reason valid for one `failed_phase` is invalid on another and cross-application is a failure, not a detail. `failure_detail` is optional prose only: it is never parsed by a consumer, never a substitute for the reason, and may not mint a cause the enum does not contain. These field names and the enum are pinned in interfaces and are NOT reopened by GATE-1d; changing them is a recorded amendment there.
- **Cold-build limiter / writer lease:** the cold-build limiter admits inspect-triggered callgraph and Tier-2 builds; its permit is awaited on a dedicated background thread with cancellation rechecked before and after acquisition, never in the poll closure. The writer lease authorizes publishing a rebuilt artifact. Lease failure or build error is (c) PHASE-FAILED carrying `failed_phase`, `failure_reason`, optional `failure_detail`, and its category attribution, never a silent stale read and never readonly-cached output presented as current.
- **Preflight / preflight form:** two distinct things, kept separate because one is a time window and the other is a payload shape. PREFLIGHT is the activity window before any phase begins — root resolution, applicable-set resolution, missing-executable discovery at resolution, and applicability-snapshot construction. THE PREFLIGHT FORM is the terminal shape used for those failures: PHASE-FAILED with an empty completed-phase list, no `failed_phase`, no numeric counts, no category summary objects, and no clean-state claim. IT STILL CARRIES A REASON: the form drops phase attribution, not the cause, so it carries an applicable preflight `failure_reason` from the closed enum plus optional `failure_detail`, and a terminal that omits the reason because it omits `failed_phase` is malformed. The form is structural, so post-preflight refusals and Tier-1 failures that can name no phase also take it under the GATE-7b interim rule; taking the form is not a claim that the failure occurred during preflight.
- **Inspect-phase log:** the server-side, per-inspect-call record of phase start, completion, duration, and terminal error, correlated by request id and carrying the producer key or category where the ID takes one. It is the artifact the completed-phase list is derived from and is read by acceptance through an in-process accessor as well as structured emission. It is explicitly NOT `run_tool_call::PhaseTrace`, the fixed-field subc dispatch-milestone recorder; building it is required work.
- **Deferred-response seam:** the `PendingResponses` / `DispatchOutcome::Deferred` registration path `handle_inspect` converts onto, plus the per-transport delivery, flush, and shutdown paths that carry one terminal frame back to the client. The poll closure on this seam is observe-only — no waits, no builds, no writes. The seam has no cancel-by-request-id operation today and its `drain_on_shutdown` clears without emitting, so emit-before-clear delivery, the inspect-shaped envelope, and per-request cancellation are new work under GATE-10 (and GATE-5 for cancellation), not reuse.
- **Admission event:** the harness-visible record emitted by this campaign's NEW cold-build limiter surface when a waiter is admitted, carrying request identity and class (inspect-triggered or maintenance). Deterministic-admission acceptance reads this event rather than log prose; today's limiter emits nothing of the kind. It and the internal per-request class/order state that ticketed ordering would require are internal and harness-facing, not user-visible or globally tunable configuration, and may not be refused as new knobs.
- **Obligated set / completion oracle:** the obligated set is the document or workspace set a snapshotted applicable server kind must have reported before its diagnostics may be called complete; the completion oracle is that kind's mechanically observable boundary proving it did. A single version-valid publish is not an oracle for a multi-member set, and elapsed quiet time is not one at all. An empty applicability snapshot does not satisfy the rule vacuously. Both are ruled per kind by GATE-9, rust-analyzer included, whose quiescence signal is part of its proof rather than a substitute for it.
- **Applicability snapshot / orphan:** the applicability snapshot is the side-effect-free resolver output — recorded as `ServerKey` (canonical root plus server kind) records until GATE-7c rules configuration identity — taken before any process start and binding for the call's whole life. An orphan is a live process group untracked by the child registry or carrying no active idle-reap deadline; a registered server still warming is not an orphan.
- **FRESH / INTERRUPTED / PHASE-FAILED:** the closed terminal taxonomy. FRESH carries mechanically verified current data; INTERRUPTED is reserved exclusively for a user-message detach or abort; PHASE-FAILED covers every mechanically observed verification failure, lease or build error, daemon shutdown, and any GATE-1-ruled ceiling. INTERRUPTED and PHASE-FAILED carry no category data presented as current, though both carry the ordered completed-phase list in the shared entry shape. A call still in phase is not a fourth terminal outcome.
- **Absence-as-zero:** the failure mode in which missing evidence is rendered as a clean result — an analyzer that never ran shown as `E0 W0`, the warm-store read emitting `server_ran: false` with zero diagnostics, or a zero-count FRESH from a server that reported one member of a multi-member obligated set. It is banned on every FRESH path: zero diagnostics are FRESH only once every snapshotted applicable kind has produced its completion proof over the full obligated set, and a root with no applicable server takes the GATE-1 terminal rather than a clean-state rendering.
- **Banned partial-result fields:** the partial-result surface a FRESH response may not carry at any depth, with top level, `scanner_state`, `summary`, and `details` as minimum containers rather than an exhaustive traversal — aggregate-side `provisional`, `pending_categories`, `stale_categories`, `incomplete_categories`, `scope_truncated`, `failed_categories`, `complete` in any valuation, the `stale` sentinel in any valuation, and per-category `status: pending|stale|failed`; diagnostics-side `provisional_counts`, `servers_pending`, `servers_not_installed`, `files_without_server`, and any `server_ran: false` payload. The ban is on partial-result FIELDS generally, not on this enumeration alone; the enumeration exists so a named-field assertion cannot go green while an unnamed equivalent ships.
- **Scope / sections:** `scope=` narrows the RESULT set and, until GATE-2 rules a narrowed snapshot, narrows neither server starts nor obligated documents nor freshness work. `sections=` selects drill-down DETAIL and never the set of categories whose freshness is required, which stays `InspectCategory::active()` until GATE-7a rules a real selector.
- **Fenced ground:** the adversarially-audited machinery — lifecycle/epoch handling, quiescence semantics, and artifact publication order — whose predicates, ordering, and visibility timing may not be ALTERED by this campaign, subject only to the non_goals carve-out permitting inspection-started idle-reap deadlines and shutdown escalation through existing child-registry/manager surfaces. Epoch, generation, and publication machinery remain banned. The fence bans alteration, not additive observation: the per-kind obligated-set and completion tracking GATE-9 requires and the inspect-phase log are required work under it. If a kind's oracle cannot be built additively, that is a recorded amendment.
- **Fresh-Tier-2 verdict / delta-engine boundary:** a DECLARED FUTURE INTERFACE minted by the alert-channel-and-bar-retirement campaign; this draft specifies no implementation or acceptance contract for that handoff.
