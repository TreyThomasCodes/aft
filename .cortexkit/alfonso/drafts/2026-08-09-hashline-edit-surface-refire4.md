## intent

Implement a hashline edit surface in AFT using a pinned revision of `~/Work/OSS/oh-my-pi/packages/hashline` (revision 45e12e5bb758198a920c6070e7e64cb33b21beac) as the semantic oracle. When a session's effective hashline mode is on, taggable reads and successful edit responses expose an agent-visible tagged representation with absolute 1-based line numbers, and the sole agent-visible `edit` name accepts the hashline patch language. Every file section requires a retained four-hex snapshot handle; verification exact-compares retained full-byte line records against one common Phase-1 baseline per canonical path; no handle state ever falls through to unchecked line-range application.

One binary and one plugin build contain both modes. Configuration plus session re-registration selects the surface per session; a session never exposes both. Tagged reads, hashline `edit` registration, edit-response tags, and MCP exposure are governed by the session's installed effective value; accepted bash read rewrites render tagged only when, additionally, the experimental bash-rewrite gate is enabled and the rewrite funnel accepts the command.

The motivating traffic analysis (queries committed with the campaign) reported 4.8% failure for match/oldString edits and 0 reported failures among 144 line-range edits — the latter establishes nothing about safety, because an in-bounds stale range mutates the wrong location silently. This campaign delivers detectable snapshot mismatch, exact recovery accounting, and correctness evidence for line-addressed editing. Whether the syntax is cheaper for models to emit remains a post-implementation LEBENCH hypothesis, not a delivered property.

V1 scope: `PUT`, `CUT`, `REM`, `MV`, line/range/gap/block addressing, `$`, named and anonymous registers, cross-file register use, boundary-echo repair, indent repair, replacement coalescing, and exact verbatim remap recovery.

## glossary

- **Per-file patch section**: a hashline patch unit headed by `[requested-path#TAG]`; the header supplies the path spelling and handle used for lookup and verification.
- **Session hashline binding**: the state atomically installed for `(canonical project root, session id)` after registration. It contains the configured value, edit-slot eligibility, effective value, snapshot store, eviction history, and register store. Requests use a captured binding rather than root-global mutable configuration.
- **Edit-slot eligibility**: whether `edit` survives final surface selection, pruning, hoisting policy, and `disabled_tools`, computed without selecting the legacy or hashline schema.
- **Effective mode**: the boolean `resolved hashline.enabled AND edit-slot eligibility` installed for a completed session registration. It selects one edit schema and governs translation, tagged reads, edit-response tags, MCP, and bash rewrites that also satisfy their experimental gate and rewrite-funnel conditions. An unregistered session is effective-off.
- **Snapshot**: an in-memory, session-owned record of one coherent read of one canonical path. It contains retained raw line records and absolute numbers, coverage, boundary evidence, recorded `total_lines`, whole-file tag, and capture provenance. Every mint scans to end of input (the whole-file tag requires it), so EOF observation is a scan invariant, not a distinguishing state. It is never persisted.
- **Raw line record**: content bytes without the line terminator plus terminator kind LF, CRLF, or none-at-EOF. BOM bytes belong to line 1. Exact verification compares both unnormalized content and terminator kind.
- **Tag / handle**: the four-hex value rendered in `[requested-path#TAG]`. Input is case-insensitive and output is uppercase. It is derived from normalized whole-file content, may collide, and authorizes nothing without unambiguous snapshot resolution and exact verification.
- **Seen line**: a line whose complete raw record is retained as eligible by the minting read. Hash-only scanning, lookahead, metadata inspection, and output-cap elision do not make a line seen. A display-truncated line remains seen because its complete record is retained.
- **Boundary evidence**: retained BOF, EOF, empty-file, predecessor, or successor facts needed to prove an addressed gap or boundary form eligible without consulting current live-file length.
- **`$` / EOF-relative resolution**: `$` and EOF-relative addresses resolve against the snapshot's recorded `total_lines` and never consult current live-file length. Every minted snapshot records `total_lines` because every mint scans to end of input.
- **Taggable read**: a successful text read of a write-eligible regular filesystem path that retains the requested eligibility domain. Untaggable outcomes mint no snapshot or tag.
- **Capture provenance**: file identity and metadata recorded to prove that one snapshot was coherently minted. It is not verification evidence and does not by itself make same-tag candidates non-equivalent.
- **Baseline**: the complete current-byte buffer loaded once per canonical path during Phase 1 and owned by that patch through Phase 2. Snapshot eviction cannot change it.
- **Equivalent snapshot candidates**: same-path, same-tag candidates with identical retained raw records, absolute coverage, and boundary evidence. They collapse to one verification view even if capture provenance differs.
- **Evicted handle**: a canonical-path/tag pair removed by deterministic snapshot residency enforcement whose bounded eviction-history record remains resident. It returns `hashline_evicted_tag` but authorizes no write.
- **Expired eviction-history record**: an eviction record discarded by the declared record or byte bound. Its later lookup returns `hashline_unknown_tag`; this deterministic transition is part of the interface.
- **Landing**: a location where stale addressed content occurs verbatim in the Phase-1 baseline. One landing is unique, two or more are ambiguous, and zero makes recovery impossible.
- **Phase 1 / Phase 2**: mutation-free parsing, lookup, exact verification, rollback-availability checks, planning, and register staging against common baselines / patch-ordered execution through backup, write, durability, format, validation, and authoritative observation.
- **Phase-1 rejection**: a pre-execution failure carrying a registered code and adjudication stage. It leaves file bytes unchanged and never returns a Phase-2 result envelope.
- **Phase-2 result envelope**: the ordered result returned after execution begins, including all-failed execution. Each planned file is classified as applied, failed, or skipped after a prior stopping failure.
- **Register**: restart-volatile session clipboard state, named by `@name` or anonymous. Phase 1 may stage request-local values; session state changes only after every planned file is written.
- **Rollback record**: an existing backup or created-file record sufficient for `aft_safety` to reverse a destructive mutation. No destructive write proceeds without one.
- **Affected region**: deterministic post-write rows retained and rendered in an edit response: changed output rows plus nearest surviving predecessor and successor, coalesced and ordered.
- **op_id**: the patch-level undo identity emitted exactly when the undo journal retains at least one record for the request. One `aft_safety` undo reverts the complete recorded operation, including a partial application.

## design

Implement the native engine in `crates/aft/src/hashline/` with modules for the pinned tokenizer and parser, raw line scanning and whole-file tag calculation, coherent snapshot capture, bounded snapshot and eviction-history storage, bounded registers, verification, request-local Phase-1 planning, Phase-2 execution, repair, exact remap recovery, affected-region rendering, and BlockResolver integration backed by AFT's tree-sitter fleet.

Rust `config_resolve` remains the sole configuration authority. Registration computes edit-slot eligibility independently of schema selection, derives the effective value, and atomically installs a session-keyed hashline binding for `(canonical project root, session id)`. The binding owns that session's effective value, snapshot store, eviction history, and register store. Translation and tool-call contexts capture the installed binding for the duration of each request; handlers do not infer mode from a root-global mutable configuration object. This permits interleaved sessions under one project root to use different modes without crossing schemas, warnings, tags, or stores.

TypeScript changes are limited to mirrored configuration, selecting the committed registration arm from the Rust-resolved and session-bound effective value, transport adaptation, response adaptation, and host display. A missing or failed session registration behaves as effective-off. Effective-value changes clear only the affected session's stores before the new binding becomes callable; same-effective-value re-registration preserves them.

The wire surface remains one agent-visible `edit` name. Gate-off translation retains the legacy schema and handler selection. Gate-on translation accepts only the hashline patch payload and routes to the native hashline handler. The effective-mode branch occurs before shared path-argument normalization and every legacy edit-shape check because the gate-on schema has no `path` argument. A session never publishes both edit schemas.

Snapshot capture opens one descriptor and performs one forward scan that derives the normalized whole-file tag, retains requested raw records and boundary evidence, records capture provenance, and records whether the scan reached EOF. Identity and observed-byte metadata are checked around the scan. Instability retries once from a new descriptor and otherwise mints no snapshot. Rows scanned only to finish hashing or establish EOF remain unseen unless retained by the requesting read semantics.

Snapshot lookup uses session, canonical path, and case-insensitive tag. Capture provenance is diagnostic rather than part of equivalence. Candidates collapse only when their retained raw records, absolute coverage, and boundary evidence are identical; otherwise lookup is ambiguous. Verification then exact-compares addressed records and anchors against the one current Phase-1 baseline. Snapshot payload eviction and eviction-history expiration are independent deterministic LRU processes under their declared bounds.

Phase 1 parses every section, resolves canonical paths and retained handles, loads one common baseline per canonical path, exact-verifies addressed records and required anchors, plans repairs and register effects, and proves that each destructive operation has a rollback mechanism. It performs no externally visible mutation. Phase 2 processes files sequentially through backup, write, formatting, validation, durability, authoritative final-byte observation, and LSP notification under one patch-level undo identity. Baseline bytes are rechecked immediately before each write. A stopping execution failure produces an ordered mutation-result envelope with an explicit per-file classification and marks later files skipped; it is not converted back into a Phase-1 rejection.

Authoritative final observations feed one affected-region renderer and snapshot minter shared by NDJSON, subc, MCP, OpenCode, and Pi. The response adapter carries deterministic tagged text, stable Phase-2 classifications, available undo identity, and the shipped host display envelope, so existing hosts can render diffs without understanding hashline-specific fields. MV uses the existing backup and created-file rollback mechanisms, durably writes the destination before unlinking the source, and invalidates removed-source snapshots without recording an eviction.

## interfaces

- CONFIG: `hashline.enabled` is a boolean defaulting to `false`, accepted at user and project tiers, resolved solely by Rust `config_resolve`, published in resolved configuration, and threaded to callers without local configuration re-reads.
- SESSION BINDING: registration computes edit-slot eligibility independently of schema selection, derives the effective value, and atomically installs it for `(canonical project root, session id)`. Translation and tool calls capture that installed binding. A session with no completed binding behaves as effective-off. Concurrent sessions under one root may expose opposite modes without sharing tags or stores.
- TOOL SURFACE: one agent-visible `edit` is registered per session. Its schema and description are the committed legacy surface when effective mode is off and the hashline patch surface when effective mode is on. `read` keeps its request schema and uses tagged rendering only when effective mode is on. `apply_patch` is unchanged.
- GATE-ON EDIT: agent arguments are exactly `{patch:string}`, with `patch` required and non-empty. Server-owned preview control remains outside the agent schema. Paths and tags come from patch headers. Translation routes only to native `hashline_edit`.
- GATE-ON TRANSLATION ORDER: effective hashline mode selects the hashline arm before shared path-argument normalization and before every legacy edit-shape check. Gate-on edit is exempt from legacy path normalization because it has no `path` argument. Any legacy edit key returns `hashline_parse_error`; it is never ignored, normalized, or routed to a legacy handler. Gate-off normalization, translation, and rejection text remain unchanged.
- EFFECTIVE-MODE WARNING: when configured on but `edit` is removed by final surface selection, pruning, hoisting, or `disabled_tools`, configure succeeds in tagless mode and emits `{code:"hashline_downgraded", reason:"edit_not_registered"}` on the configure-warnings channel.
- REJECTION CODES: `hashline_missing_tag`, `hashline_malformed_tag`, `hashline_unknown_tag`, `hashline_evicted_tag`, `hashline_ambiguous_tag`, `hashline_stale_tag`, `hashline_unseen_line`, `hashline_boundary_ineligible`, `hashline_untaggable_path`, `hashline_register_overflow`, `hashline_backup_unavailable`, and `hashline_parse_error`. `hashline_baseline_drift` is the stable Phase-2 stop reason paired with per-file `failed_baseline_drift`. Registry fixtures fix each code or stop reason's transport status, required fields, mutation and store guarantees, precedence, and availability-correct steering.
- REJECTION STAGE: every Phase-1 rejection carries a required `stage` with one of `parse`, `header`, `path`, `resolution`, `eligibility`, `verification`, `recovery`, `register`, or `baseline` (the single canonical enum; REJECTION PRECEDENCE enumerates exactly this order). A code reachable from multiple stages is disambiguated by `stage`. `hashline_ambiguous_tag` at `resolution` means non-equivalent retained candidates and steers to a fresh tagged read; at `recovery` it means multiple verbatim landings and steers to re-addressing against current tagged content. `hashline_stale_tag` at `verification` means a required-anchor mismatch and steers to a ranged tagged re-read; at `recovery` it means the addressed content no longer exists verbatim anywhere.
- HEADER-SYNTAX BOUNDARY: a payload that does not parse as the hashline patch language, including legacy edit keys in gate-on mode, is `hashline_parse_error` at `stage:"parse"`. A recognizable per-file header with no `#TAG` is `hashline_missing_tag`; a present tag that is not exactly four hexadecimal digits is `hashline_malformed_tag`. Both header failures use `stage:"header"`.
- REJECTION PRECEDENCE: adjudication order is request shape and parse; required header and four-hex syntax; existing path validation, taggability, and rollback availability; candidate lookup and equivalence; seen coverage; boundary and anchor eligibility; exact raw-record verification; and verbatim recovery. The first failing stage determines the code and reported stage.
- SNAPSHOT LOOKUP: the key is session, canonical path, and case-insensitive tag. Candidates with identical retained raw records, absolute coverage, and boundary evidence collapse even if capture provenance differs. Other multiplicity returns `hashline_ambiguous_tag` at `stage:"resolution"`. Every section for one canonical path selects one equivalent verification view and one current Phase-1 baseline before mutation.
- EVICTION LOOKUP: a handle removed from snapshot residency returns `hashline_evicted_tag` only while its bounded eviction-history record remains resident. Deterministic expiration of that record changes the result to `hashline_unknown_tag`. In-patch MV invalidation and session clearing create no history record and return unknown immediately.
- PHASE-2 ENTRY: a request that passes Phase 1 returns the mutation-result envelope once execution begins, including when no file reaches an applied state. Phase-2 failures are not reclassified as parse or handle rejections.
- PER-FILE CLASSIFICATIONS: ordered results use `applied`, `applied_with_validation_failure`, `applied_tag_unavailable`, `failed_backup`, `failed_write`, `failed_durability`, `failed_source_unlink`, `failed_baseline_drift`, and `not_attempted`. Formatter failure retains the otherwise applicable `applied*` classification and adds `format_skipped_reason`. A stopping failure marks all later planned files `not_attempted`.
- MUTATION RESPONSE: mutation-result envelopes carry ordered per-file results, available final tags, an optional top-level stop reason, and `remap_recovery:{old_span,new_span,applied,backup_id?}` when recovery is reported. `applied:true` requires a real backup identifier; `applied:false` forbids one and denotes a non-mutating proposal. The envelope carries `op_id` exactly when the undo journal retains at least one record for the request, including a record created before a later failure.
- RESPONSE FLAGS: existing completion flags retain their shipped meanings. Complete means every planned file has an `applied*` classification; partial means at least one but not every planned file does; all-failed means none does. Hashline-specific completion or register-commit details do not redefine keys consumed by existing hosts.
- BACKUP AVAILABILITY: a destructive operation known during Phase 1 to lack a rollback mechanism rejects as `hashline_backup_unavailable` at `stage:"path_validation"`. Dynamic backup creation failure is `failed_backup`, writes no bytes for that file, and stops later files. Existing MV destinations require a backup record; newly created destinations use a created-file rollback record. Responses never advertise an undo identity that does not exist.
- DISPLAY ENVELOPE: hashline fields supplement rather than replace the shipped mutation display envelope. Responses retain agent-visible `output`, shipped title and `filePath` behavior, and the `metadata.diff` and patch-order-stable `metadata.files[]` forms consumed by current OpenCode adapters. A host that reads only the shipped envelope must render hashline single-file, multi-file, and MV results correctly.
- TEXT TAG CARRIER: every successfully written path with an authoritative final tag emits `[requested-path#TAG]` plus deterministic, renumbered affected-region gutters in agent-visible text on NDJSON, subc, MCP, and OpenCode. `applied_tag_unavailable` and successful source removal emit explicit notices instead. Structured fields supplement but never replace text.
- MV RESPONSE: ordered per-file results describe destination before source and retain each path's requested spelling. Destination and source outcomes remain independently truthful. Destination durability precedes source unlink, and source-unlink failure leaves the successful destination mutation recoverable under the shared `op_id`.
- PREVIEW RESPONSE: preview reuses the shipped preview envelope and is explicitly marked as preview. It contains no `op_id`, backup identifier, final tag, snapshot mint, undo record, or session-register commit. Phase-1 failures use the same registered rejection code and stage that apply would return.
- UNDO: when present, `op_id` is consumed by the existing patch-level `aft_safety` undo path. Existing MV destinations use the existing backup mechanism; newly created destinations use the existing created-file rollback record; source restoration belongs to the same operation. Partial applications retain one shared operation identifier.

## constraints

OWNER RULINGS (refire 4) — normative; these supersede any conflicting sentence elsewhere in this document. Each closes one round-3 blocker:

- EVICTION HISTORY IS BOUNDED: the per-session eviction-history record is a bounded LRU of `MAX_EVICTION_RECORDS = 256` (path, tag) entries. While a record is retained, a resolving handle reports `hashline_evicted_tag`; once the record itself is evicted, the same handle reports `hashline_unknown_tag`. This evicted→unknown transition is accepted, documented in both codes' steering text (identical recovery: re-read), and locked by an acceptance row that overflows the history and asserts the transition. Exact eviction history is NOT unbounded metadata.
- PHASE-2 OUTCOME TAXONOMY: a Phase-2 failure is NEVER a patch-level rejection — it is a mutation-result envelope (success:true, complete:false) with a required per-file `classification` enum: `applied`, `applied_with_validation_failure`, `applied_tag_unavailable`, `failed_backup`, `failed_write`, `failed_durability`, `failed_source_unlink`, `failed_baseline_drift`, `not_attempted`. Files after the failing file are `not_attempted`. `op_id` appears iff at least one undo-journal entry was created (a file that failed after its backup was taken still yields op_id; an all-failed Phase 2 with zero journal entries omits op_id and reports every file's failure classification). Patch-level rejection codes (the `hashline_*` registry) are Phase-1-only, plus `hashline_backup_unavailable` below.
- SNAPSHOT-CANDIDATE EQUIVALENCE: two retained snapshots for the same (canonical path, tag) are equivalent iff their verification-relevant retained evidence is identical — raw line records, coverage set, and boundary evidence. Descriptor metadata (capture time, provenance, baseline identity) never participates. Byte-identical re-reads therefore collapse to one candidate and resolve cleanly; `hashline_ambiguous_tag` requires genuinely divergent retained evidence.
- STAGE DISCRIMINATOR: every rejection carries a required `stage` field whose values are exactly the adjudication stages (parse, header, resolution, eligibility, verification, recovery, register, baseline). The two ambiguity sources are thereby machine-distinguishable: `{code: hashline_ambiguous_tag, stage: resolution}` (two non-equivalent snapshots — recovery: re-read) vs `{code: hashline_ambiguous_tag, stage: recovery}` (two verbatim landings — recovery: re-address). Fixtures assert the stage for both, and for every other code its single legal stage.
- BACKUP-UNAVAILABLE DESTRUCTIVE OPS: when backups are disabled or yield no restore record, any operation that would destroy bytes it cannot restore refuses in Phase 1 with `hashline_backup_unavailable` (stage: baseline): MV onto an existing destination, and REM/CUT/PUT whose target file cannot be backed up. New-destination MV proceeds because its rollback record (created-file deletion) is a real undo identity under the shared op_id. There is no `unrecoverable: true` outcome anywhere: every hashline mutation either holds a restore-capable rollback record or refuses in Phase 1. Acceptance rows run the MV-existing-destination and plain-PUT cases with backups disabled and assert the refusal for both.
- PARSE/HEADER CODE BOUNDARY: grammar/shape failures (body violates the patch grammar, non-string patch, empty patch) are `hashline_parse_error` (stage: parse); a recognizable section header lacking `#TAG` entirely is `hashline_missing_tag` (stage: header); a present tag that is not exactly four hex digits is `hashline_malformed_tag` (stage: header).
- SLICE OWNERSHIP AND FENCES: the delivery plan's slice list is amended: slice 3 (stores) exits on the snapshot-residency and eviction-history rows of A6; slice 5 (registers) exits on the register-bound rows of A6; slice 6 (transactions) additionally exits on A10 (preview mutates nothing). Every slice's file fence is disjoint; the schema/manifest/governed-artifact regeneration belongs EXCLUSIVELY to the final registration slice (no other slice touches `subc_tool_schemas.json`, governed manifests, or schema build scripts), which removes the fence overlap the mechanical check rejected.
- UNREGISTERED SESSIONS (restated from the session-binding constraint for request-time surfaces): a session with no completed registration has effective mode off — tagless reads, no hashline edit, no snapshot minting. Bash rewrites additionally require their own experimental gate and funnel acceptance; effective mode alone never suffices.

- ENGINE AND ARTIFACT: both effective modes ship in one binary and one plugin build. Configuration plus session re-registration switches modes; rebuilding is not a permitted switch mechanism.
- CONFIGURATION AUTHORITY: `hashline.enabled` is a boolean defaulting to `false` at user and project tiers. It is added to `RawAftConfig` under `deny_unknown_fields`, resolved Rust `Config`, `apply_resolved_config`, and the mirrored TypeScript Zod schema. It is not a privileged project-tier key and must not appear in the project-tier drop list. Rust `config_resolve` is the sole resolver; callers do not independently re-read configuration.
- SESSION BINDING AND EFFECTIVE MODE: AFT maintains hashline state keyed by `(canonical project root, session id)`. Registration first computes `edit_slot_survives` from final surface selection, pruning, hoisting policy, and `disabled_tools` without choosing an edit schema. It then computes `effective = resolved hashline.enabled AND edit_slot_survives` and atomically installs the session binding containing the configured value, edit-slot eligibility, effective value, snapshot store, and register store. The installed effective value selects exactly one registered `edit` schema and governs translation, reads, response carriers, MCP, and accepted bash rewrites. Root-global mutable configuration is not the mode authority for an already bound session. A session without a completed registration has effective mode off, renders tagless reads, exposes no hashline edit surface, and mints no hashline snapshot. Configured-on with no surviving `edit` installs effective false and emits `{code:"hashline_downgraded", reason:"edit_not_registered"}` without rejecting configuration or forcing registration.
- SESSION LIFECYCLE: each request captures its installed session binding into its translation and tool-call contexts. Request handling never re-reads root-global configuration to infer mode. Concurrent sessions under one project root may use different effective modes. Changing one session's effective value requires re-registration and atomically clears only that session's snapshot and register stores before the new binding becomes callable, making old handles unknown. Same-effective-value re-registration preserves those stores. Failed registration does not install a partial binding. Session teardown and restart remove the applicable bindings and stores. No agent-visible generation argument or stale-generation rejection protocol is introduced.
- TRANSLATION ORDERING: in effective hashline mode, the `edit` hashline arm is selected before shared path-argument normalization and before every legacy edit-shape check. Gate-on `{patch}` calls have no `path` argument and are exempt from legacy path normalization. Legacy edit keys in gate-on mode return `hashline_parse_error`; no legacy rejection message or handler is reachable. Gate-off normalization, dispatch, and rejection text remain byte-identical to current goldens.
- ORACLE PIN: the semantic oracle is oh-my-pi revision `45e12e5bb758198a920c6070e7e64cb33b21beac`, package `packages/hashline`. The full revision is recorded in the fixture manifest. Fixtures are generated from that revision, frozen, and committed. Regeneration is reviewed and hermetic, and Rust CI does not require Bun.
- TAG ALGORITHM: normalize the whole file by stripping `[ \t\r]+` immediately before each `\n` and at end of input, compute `xxHash32(normalized, seed 0) & 0xffff`, render four uppercase hexadecimal digits, and match input case-insensitively. The Rust implementation is pinned or vendored and proven against oracle vectors. A matching tag is only a lookup key and may collide.
- VERIFICATION: snapshots retain raw, unnormalized records. Addressed records and required anchors exact-compare content bytes and terminator kind against one common Phase-1 baseline per canonical path. A trailing-whitespace-only change may preserve the normalized tag but cannot bypass exact verification when it changes an addressed record or required anchor. This exact-byte AFT safety rule is normative; any looser oracle row is recorded as a reviewed deviation rather than changing the rule.
- LINE-BYTE MODEL: the common scanner splits on `\n`. Records contain content bytes without the terminator and terminator kind LF, CRLF, or none-at-EOF. A `\r` immediately before `\n` belongs to CRLF; interior `\r` is content. BOM bytes belong to line 1. A trailing terminator creates no extra record. Empty files have zero records and remain taggable. Missing final newline produces a final record with no terminator. Snapshots have no wire or disk serialization.
- COHERENT SNAPSHOT CAPTURE: retained records, whole-file tag, capture provenance, and EOF observation for one snapshot come from one coherent file version. Minting uses one descriptor and one forward scan, updating the normalized whole-file hash while retaining the requested eligibility records. Continuing after a requested range does not make later rows seen. File identity, size, modification metadata, and observed byte count are checked around the scan. Instability retries once from a new descriptor; repeated instability follows the ordinary read-I/O contract and mints no snapshot. Whole-file reads use the same scan rather than an independent hash pass.
- BOUNDARY ADDRESSING: BOF, EOF, `$`, line, range, gap, block, one-sided-gap, one-line, and empty-file behavior follows the pinned oracle corpus. `$` and EOF-relative forms resolve against the snapshot's recorded `total_lines` and never against current live-file length. Gap insertion requires both boundary lines to be seen except for oracle-permitted one-sided BOF, EOF, and empty-file forms.
- TAGGABLE READ: a read is taggable only when it successfully reads a write-eligible regular filesystem path as text and retains the requested eligibility domain. Empty regular files are taggable. Directories, devices, sockets, binary or invalid-UTF-8 files, media responses, virtual or registered background artifacts, missing paths, paths failing write eligibility, whole-file size refusals, empty ranges, and beyond-EOF ranges mint no snapshot or tag. Read-only regular files may be displayed but are untaggable.
- READ RENDERING: gate-on taggable reads render `[<requested-path>#TAG]` and oracle-compatible absolute `N:content` gutters. Structured responses also carry the lossless agent-supplied `requested_path`. Existing whole-file refusal, 50 KiB output cap, and 2000-character line-truncation thresholds remain. Elided rows are unseen, and the gate-on elision notice names their absolute unaddressable range. Display truncation retains the complete verification record, so the row remains eligible. Every read mints a separate snapshot version. The locked agent-visible golden is the text after the existing response formatter has composed its header, body, and footer.
- BASH REWRITES: `cat`, `head`, and `tail` use tagged rendering only when `experimental_bash_rewrite` is enabled, the existing rewrite funnel accepts the command, and effective mode is on. Tail uses a forward scan with bounded selected-row retention and determines absolute numbering at EOF, including for files exceeding the whole-file display cap. No reverse scanner is introduced.
- EDIT-RESPONSE SNAPSHOT: after authoritative final-state observation, each written path that remains a readable regular file receives a fresh snapshot and text carrier. The affected region contains inserted or surviving replacement rows plus the nearest surviving predecessor and successor when present. Pure deletion retains its nearest surviving predecessor and successor; insertion into an empty file retains all inserted rows; deletion producing an empty file retains zero rows plus empty-file boundary evidence. Overlapping or adjacent regions coalesce and render in ascending output-line order. A successfully removed MV source emits no final tag or snapshot. `applied_tag_unavailable` emits an explicit notice and requires a tagged re-read before chaining.
- HANDLE RESOLUTION: lookup is by session, canonical path, and case-insensitive tag. Capture provenance is retained for coherent-read diagnostics but is not part of candidate equivalence. Same-key candidates collapse only when retained raw records, absolute coverage, boundary evidence, and EOF-observation state agree. Any verification-relevant difference returns `hashline_ambiguous_tag` at `stage:"candidate_lookup"`; resolution never chooses newest or first. After lookup, addressed records and required anchors exact-compare against the one current Phase-1 baseline for the canonical path. Every section for one canonical path must resolve to one equivalent verification view before mutation.
- SNAPSHOT RESIDENCY: snapshot payloads are per-session bounded state with `MAX_SNAPSHOT_PATHS = 30`, `MAX_VERSIONS_PER_PATH = 4`, and `MAX_SNAPSHOT_TOTAL_BYTES = 64 MiB`. Eviction is deterministic LRU within path and byte budgets, oldest-version-first within a path.
- EVICTION HISTORY: eviction-history metadata is bounded by `MAX_EVICTION_RECORDS = 256` (one constant; no separate byte bound). Evicting a resident snapshot records `(canonical path, case-folded tag)` in a deterministic LRU history. Lookup returns `hashline_evicted_tag` only while that record remains resident. Exceeding the record bound discards the oldest records deterministically; later lookup for a discarded record returns `hashline_unknown_tag`. This transition is normative and tested. In-patch MV source invalidation, session teardown, restart, and effective-mode clearing create no eviction-history record, so subsequent use returns `hashline_unknown_tag`.
- REGISTER BOUNDS: `MAX_NAMED_REGISTERS = 64`, `MAX_REGISTER_BYTES = 8 MiB`, and `MAX_REGISTER_TOTAL_BYTES = 32 MiB`. Exceeding any bound rejects the whole patch in Phase 1 as `hashline_register_overflow`. Named registers are never silently evicted.
- PREVIEW AND REGISTERS: apply-mode Phase 1 may stage request-local register values so later operations in the request can consume them. Preview may calculate plan-local simulated values solely to render the complete plan, but does not capture into or commit against the session register store. Preview creates no file bytes, snapshots, backups, undo records, or `op_id`. Apply commits staged registers once at patch end only after every planned file is written.
- CROSS-FILE TRANSACTIONS: Phase 1 parses all sections, validates paths, resolves snapshots, loads one common baseline per canonical path, verifies records and anchors, bounds-checks register effects, establishes whether every destructive operation has an available rollback mechanism, and plans every operation without externally visible mutation. Any Phase-1 failure rejects the whole patch. Phase 2 processes files in patch order under one optional `op_id`. Baseline drift, backup failure, write failure, destination-durability failure, and source-unlink failure stop later files. Formatter failure does not stop the file or later files. Syntax-restoration or validation-execution failure leaves bytes applied and yields `applied_with_validation_failure`; tags come from authoritative on-disk bytes. Final-read failure yields `applied_tag_unavailable`. LSP notification is best effort. Previously applied files stand after a later failure.
- BACKUP AND ROLLBACK SAFETY: no destructive write proceeds without a rollback record capable of restoring the overwritten or removed bytes. If rollback availability is known to be absent during Phase 1, the patch rejects as `hashline_backup_unavailable` at `stage:"baseline"`. If creating the required backup fails during Phase 2, that file is `failed_backup`, no write occurs, and later files are skipped. An existing MV destination requires a real backup record; a newly created destination uses the existing created-file rollback record. Unique stale recovery always holds a real backup identifier at apply time because backups are a precondition of hashline apply (a no-backup state refused in Phase 1); preview renders recoveries as non-mutating proposals. A response never advertises an undo handle that does not exist.
- PHASE-2 RESULT TAXONOMY: once a request enters Phase 2 it always returns the complete mutation-result envelope. `success` is `true` when at least one file reached an `applied*` classification and `false` when none did (all-failed execution), in both cases carrying the full per-file results, mutation states, and any `op_id`; the rendered text leads with applied/failed counts so field-stripping hosts still render the truth. Ordered per-file classifications are `applied`, `applied_with_validation_failure`, `applied_tag_unavailable`, `failed_backup`, `failed_write`, `failed_durability`, `failed_source_unlink`, `failed_baseline_drift`, and `not_attempted`. A formatter failure retains the applicable `applied*` classification and adds `format_skipped_reason`. Every stopping failure marks all later planned files `not_attempted`. Existing envelope completion flags retain their shipped meanings: complete means every planned file reached an `applied*` classification; partial means at least one but not every planned file did; all-failed means none did. The response carries `op_id` exactly when the undo journal retains at least one record for the request, including a record created before a later failure.
- MV SAFETY: destination durability precedes source unlink. Undo restores the source and restores an existing destination or removes a destination created by the patch. Successful source removal invalidates source snapshots without recording an eviction. Destination and source outcomes remain independently truthful.
- BASELINE INTEGRITY: immediately before each Phase-2 write, current bytes must equal the patch-owned baseline, using size and mtime only as a fast path and byte comparison on doubt. Drift produces per-file `failed_baseline_drift` with stop reason `hashline_baseline_drift`, does not write that file, stops later files, and leaves prior applications under the shared `op_id`. Canonical-path keying uses existing path validation and symlink resolution.
- STALE RECOVERY: recovery searches only for exact verbatim addressed content. Exactly one landing auto-applies, carrying the real backup identifier that the backups-precondition guarantees; under preview the same landing renders as a non-mutating proposal. Multiple landings reject `hashline_ambiguous_tag` at `stage:"recovery"`; zero landings reject `hashline_stale_tag` at `stage:"recovery"`. Recovery never claims an undo handle that does not exist.
- PATH LIFECYCLE: a handle never authorizes a write without exact verification at the same canonical path. Handles do not transfer to another path. A byte-identical rewrite or delete-and-recreate remains usable when retained verification evidence is unchanged. After an in-patch MV, later use of a source-path handle returns `hashline_unknown_tag`; the response supplies a destination tag when authoritative final bytes are available.
- HOST DISPLAY: hashline results retain the shipped mutation display envelope. Single-file results use the standard `filePath` and diff metadata contract; multi-file results use first-file `filePath` and patch-order-stable `metadata.files[]`. MV displays the destination diff and names the source. Hashline structured fields supplement rather than replace the envelope consumed by existing hosts.
- REJECTION CONTRACT: failures before Phase 2 use registered rejection codes, carry the enumerated stage that produced them, leave bytes unchanged, preserve stores where applicable, and steer only to surfaces available in that session. Adjudication order is request shape and parse; required header and tag syntax; path validation, taggability, and rollback availability; candidate lookup and equivalence; seen coverage; boundary and anchor eligibility; exact verification; and verbatim recovery. Phase-2 baseline drift and other execution failures use the mutation-result taxonomy rather than being reclassified as Phase-1 rejections. Where one code is reachable from multiple stages, the stage and steering are stage-specific.
- PERFORMANCE METHOD: serial Rust tests use a committed 1 MiB fixture with a pinned checksum, three warm-ups, and ten timed repetitions. Median tag computation is at most 1 ms. Gate-on versus gate-off whole-file read-render median regression on the same fixture is at most 10%. A channel-0 test with the snapshot store at its configured maximum proves that the health reply path does not access either hashline store.
- GOVERNANCE: motivating queries and their observation window are committed. Both effective-mode schema arms and governed manifests are locked. Oracle fixtures are generated independently of AFT, repair negatives are mutation-checked, and Windows CI is authoritative for path and CRLF behavior.
- DELIVERY PLAN: implementation uses exactly nine slices with CI exit evidence, and every acceptance row A1-A14 is owned by at least one slice: (1) oracle hash parity closes A2 hash vectors; (2) raw scanner closes the remaining A2 byte-model fixtures; (3) snapshots, read rendering, residency, and eviction history close A3 and the snapshot portions of A6; (4) parser, lookup, and verifier close A1 and A4; (5) apply, repair, and registers close A1 repair controls, A5, and the register portions of A6; (6) transactions, MV, baseline drift, and preview close A8, A10, and A12; (7) remap recovery closes A9; (8) registration, transports, effective-mode session binding, and host integration close A4, A7, A11, and A14; and (9) performance and release gates close A13 and FINAL GATES.

## non_goals

- The LEBENCH/deepSWE benchmark itself: the owner runs it post-implementation; this campaign delivers the benchmarkable artifact (one config flag selects either arm on identical builds, proven by acceptance).
- Removing or deprecating the legacy edit surface, or changing the default: `hashline.enabled` stays false by default; sunset decisions require later benchmark and production evidence.
- omp's bash interceptor posture (refuse-and-bounce): accepted `cat`/`head`/`tail` rewrites continue through AFT's transparent read funnel; no new bash-blocking rules.
- Bespoke JSX-aware repair code: JSX fixtures are ordinary oracle rows; a JSX mismatch either fails parity or becomes a registered BlockResolver-span deviation; exactly TWO deviation categories are sanctioned (BlockResolver spans, and exact-byte verification rows where AFT's stricter safety rule supersedes a looser oracle row per the VERIFICATION constraint), each registered with a written justification and a control that fails the suite if the implementation stops deviating; anything else requires a spec revision.
- Mandatory tags for the legacy surface or any tool not named `edit`: gate-off behavior is byte-identical to today.
- Tags minted by grep, search, or outline: v1 tags originate only from taggable reads, accepted read rewrites, and successful hashline edit responses.
- `ast_edit` or any other omp tool: this campaign ports the hashline read/edit surface only.
