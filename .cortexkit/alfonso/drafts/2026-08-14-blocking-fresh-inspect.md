## intent


Agents ignore AFT's code-health surfaces for fixture-checkable reasons. On the passive surface, the status bar shows stale counts with a `~` disclaimer, renders analyzer absence as `E0 W0`, and presents project-wide aggregates that are not tied to the current task. Retirement and replacement of that passive surface belong to the alert-channel-and-bar-retirement campaign. On the explicit surface owned here, `aft_inspect` can return cache-with-disclaimers such as `provisional` and `pending_categories`, can treat missing diagnostics as zero, and can present stale cached data as usable. This campaign removes those explicit-inspect behaviours; it does not remove the project-wide summary mode of a bare `aft_inspect`.

These are four observed behaviours, not five: stale counts, analyzer absence-as-zero, project-wide aggregates, and explicit-inspect cache-with-disclaimers. The first three remain the alert-channel-and-bar-retirement campaign's responsibility; the explicit-inspect behaviour is owned here.

This campaign makes explicit inspection authoritative while leaving passive notification design to the alert-channel-and-bar-retirement campaign. Wake-digest rendering, status-bar retirement, alert formatting, and their byte-goldens are outside this campaign. Inspect-side deferred delivery, the existing status-bar write encountered during that conversion, plugin copy, and the shared release boundary remain in scope here.

1. **Blocking-fresh inspect.** An explicit `aft_inspect` produces no progress frames and, whenever it terminates, exactly one terminal response. A FRESH response contains data mechanically verified against the inspected tree for every category required by the current category contract. Until GATE-7a rules otherwise, every member of `InspectCategory::active()` is required and `sections=` changes drill-down detail only.

2. **Mechanical freshness.** Diagnostics require a version/epoch-valid result plus a completion proof over the obligated document set for every snapshotted applicable server kind. Rust-analyzer's quiescence signal is part of that kind's completion proof, not a substitute for it: every supported kind, rust-analyzer included, has its obligated set and mechanically observable completion boundary ruled by GATE-9. An EMPTY applicability snapshot does not satisfy this vacuously — a root with no applicable server is the no-applicable-analyzer terminal GATE-1 rules, and until that ruling lands it may render neither zero diagnostics nor any clean-state claim. Tier-2 requires either stat verification of persisted artifact identity or rebuild-completed-and-published after any required callgraph work, with the generation pointer swap observed. Wall-clock age, debounce, quiet time, cached prose, and the wait-stamp are not freshness evidence. Inspect-triggered rebuild admission is an intent rather than a terminal-delivery guarantee: it should be prompt subject to the cold-build limiter and writer lease, while acceptance asserts the specific scheduling claims below.

3. **Auditable cost.** Every FRESH response carries a wait-stamp with human-readable cost text and an ordered completed-phase list. The logical phase-entry shape is `{id, producer?, category?, also_satisfied?: [category,...]}`; `also_satisfied` is present only for a physical work unit that freshened categories beyond its primary category, and consumers treat absence as empty. The closed IDs and attribution rules are defined in constraints. The list contains completed verification or work phases, not merely phases on which the caller blocked, and is derived from the server-side inspect-phase log rather than assembled independently. A warm stat-verified result therefore lists `stat_verification` while its text states that no blocking wait occurred. An empty list means no phase completed; it does not mean a warm hit.

4. **Explicit non-fresh outcomes.** Whenever inspect terminates without freshness, it returns INTERRUPTED or PHASE-FAILED and presents no category counts as current. Both non-fresh terminals carry the SAME ordered completed-phase list and the same entry shape the wait-stamp uses — empty in the preflight form — with PHASE-FAILED additionally carrying `failed_phase`, `failure_reason`, optional `failure_detail`, and the `failed_phase` producer or category detail where that ID takes one; carrying that list is a cost record, not a counts channel. PHASE-FAILED requires a mechanically observable failure, daemon shutdown, or a ceiling or failure signal ruled by GATE-1. Elapsed silence alone is not failure evidence. If no ceiling or mechanical signal exists, an unquiesced call may remain in phase until interruption or shutdown; the closed terminal taxonomy is not an unconditional liveness guarantee.

5. **Scope semantics.** `scope=` narrows results. Until GATE-2 rules a narrowed applicable-server snapshot, it does not reduce server starts, obligated documents, or freshness work. `sections=` narrows detail, not the required category set. No deadline-truncated scoped result is permitted.


## constraints



- **Honest reporting.** "Fresh" claims must be mechanically true. The verification tickets are: document version or epoch match, the server-kind diagnostics completion oracle (GATE-9) including rust-analyzer quiescence where that server applies, stat-verified artifact identity, rebuild-completed-and-published (generation pointer swap observed), and, for todos and metrics, an in-call computation over the stat-verified file list. Wall-clock age and wait-stamp text are NOT freshness evidence. The protocol.rs tri-state convention (`success` + `complete` + named gap fields) remains the honesty convention for commands that are ALLOWED to be partial. Blocking `aft_inspect` is EXPLICITLY EXEMPT: it does not use partial-success at all. Stated without an or-clause so FRESH cannot swallow its own negation: a FRESH terminal inspect response carries mechanically verified data for EVERY requested category, plus the wait-stamp; if any requested category cannot be verified, the call is not FRESH — a verification failure is PHASE-FAILED; INTERRUPTED is reserved exclusively for a user-message detach or abort. A FRESH response contains, RECURSIVELY (top level, `scanner_state`, `summary`, `details`), none of `provisional`, `provisional_counts`, `pending_categories`, `stale_categories`, `incomplete_categories`, `scope_truncated`, `servers_pending`, `servers_not_installed`, `files_without_server`, any `server_ran: false` payload, `failed_categories`, `complete` in any valuation, the `stale` sentinel in any valuation, per-category `status: pending|stale|failed` sentinels, or stale-with-counts. `incomplete_categories` is named explicitly because `build_inspect_payload` emits it UNCONDITIONALLY under `scanner_state`, so a generic ban plus a named-field assertion that omits it goes green while the field ships; `server_ran: false` is named for the same reason on the diagnostics side, since `collect_warm_working_set` / `DiagnosticsCollection::into_payload` emit it as the absence-as-zero shape. The ban is on partial-result FIELDS generally, not on those names.

- **The FRESH payload has a positive shape, not only prohibitions.** Specified by prohibition alone, no consumer and no golden can be written. Pinned NOW at the logical level, with exact wire spelling deferred to GATE-1d: a FRESH response carries a wait-stamp with (i) a human-readable text field and (ii) an ORDERED `phases` array whose entries are records `{id, producer?, category?, also_satisfied?: [category,...]}`. `id` is a member of the closed phase-ID set below and an unknown ID is a failure. `producer` is the stable server identifier; it is PRESENT ON EVERY `lsp_start` AND `lsp_quiescence` ENTRY — including on a single-server root, so goldens and consumers never branch on server count — and ABSENT on `callgraph_ready`, `tier2_rescan`, `stat_verification`. `category` is the canonical `InspectCategory` wire name; it is PRESENT on `callgraph_ready`, `tier2_rescan`, and `stat_verification` entries, which are per-category work, and ABSENT on the two LSP entries. Neither attribution dimension may be encoded by minting a new phase ID. `also_satisfied` is PRESENT iff one physical unit of work freshened additional categories beyond the entry's primary `category` (the shared-callgraph case), and is ABSENT otherwise; consumers MUST treat absence as an empty list.
  THE ARRAY IS THE COMPLETED-PHASE LIST, NOT A BLOCKED-ON LIST, stated so it cannot contradict the warm arm: it contains every verification or work phase whose completion the inspect-phase log recorded for the call, whether or not the caller blocked on it. A warm call whose Tier-2 categories were proved current by stat-verification therefore lists a `stat_verification` entry per verified category and its human text states that no blocking wait was incurred; an EMPTY `phases` array means no phase completed at all, and a stamp is never omitted. Repeated bare IDs with no `category` attribution are forbidden, because one inspect runs several Tier-2 categories and may verify, build, or rescan more than once, and PHASE-FAILED must be able to name which category's phase failed. If one physical callgraph build satisfies several categories, the log records the admitting category once and `also_satisfied` as the ordered, duplicate-free additional categories; the field is absent when no additional category was freshened, and duplicating the build as multiple executions is a failure. Array order is completion-log order; concurrent phases need not have a deterministic cross-phase order, but each entry remains attributable and per-category ordering (`callgraph_ready` before that category's `tier2_rescan`) is preserved.
  THE ENTRY SHAPE IS SHARED ACROSS ALL THREE TERMINALS, so a consumer parses one shape rather than one per outcome: FRESH carries the wait-stamp (human text plus the ordered array); (b) INTERRUPTED and (c) PHASE-FAILED carry the same ordered completed-phase list, built from the same entry records under the same attribution rules, and (c) additionally carries `failed_phase`, `failure_reason`, optional `failure_detail`, and the `failed_phase` attribution detail where that ID takes one. The preflight form is exactly that list EMPTY. Carrying the list on a non-fresh terminal is NOT a counts channel: the (b)/(c) prohibition on numeric category counts, category summary objects, and any details payload readable as a current result is unaffected by it, and a completed-phase entry may never be rendered as a per-category result.
  GATE-1d additionally rules: the wire field names for the stamp, its entries, and the `category`/`producer`/`also_satisfied` detail fields; the taxonomy label field name and spelling; and — by ENUMERATION, not by residue — which of today's `scanner_state` keys survive the field ban (`tier2_last_run`, `tier2_trigger_reason`, `disabled_categories` are unaccounted for after the banned keys are removed). Acceptance asserts the surviving key set POSITIVELY as well as by absence.

- **Named emitters, BOTH SIDES — the Tier-2 list alone does not cover diagnostics.** Tier-2/aggregate emitters of banned fields: `summary_for` / `status_summary` / `computed_summary_for` (the stale-with-cached-payload branch inserting the `stale: true` sentinel while keeping counts) and `build_inspect_payload` (which also emits `incomplete_categories`). SEPARATELY NAMED, because they are a different code path and a different failure: the diagnostics-side emitters are `diagnostics_summary_for` (the incomplete/pending branch emitting `provisional_counts`, `status`, `servers_pending`, `servers_not_installed`, `files_without_server` while zeroing top-level counts) and `collect_warm_working_set` / `DiagnosticsCollection::into_payload` (the warm-store read producing `server_ran: false` with zero diagnostics — the absence-as-zero shape intent names). FRESH must take none of these branches. CRITICAL FOR TEST DESIGN: `run_diagnostics_category` today returns `JobOutcome::Fresh { payload }` UNCONDITIONALLY — its honesty lives inside the payload, not in the outcome variant. Therefore every freshness assertion in this campaign is PAYLOAD-SHAPED (field presence/absence and verified-count identity), never `JobOutcome`-variant-shaped; a variant-only assertion passes vacuously on the diagnostics path and proves nothing.

- **The existing inspect deadline machinery is RETIRED, not relabelled (named conversion sites, BOTH deadline families) — and retirement is distinguished from a ruled failure ceiling.** Today `handle_inspect` bounds Tier-2 with `direct_tier2_wait_budget` plus `receive_direct_tier2` against an `Instant` deadline, treats `JobOutcome::Pending` / `JobOutcome::Stale` as a returnable result, and compensates afterwards with `ctx.request_tier2_refresh_pull()` and the `pending_tier2_paths` / `force_paths_completed` bookkeeping; the deadline also travels through `tier2_run_with_reuse_direct` / `wait_for_tier2_reuse_until`. THE DIAGNOSTICS DEADLINE IS RETIRED TOO AND IS NAMED SEPARATELY: `INSPECT_DIAGNOSTICS_DEADLINE`, `collect_scoped_diagnostics` / `collect_scoped_diagnostics_until`, and the `deadline` parameter of `LspManager::wait_for_file_diagnostics` on this path. The retirement also covers every environment or debug override of those conversion sites, including `AFT_INSPECT_DIRECT_TIER2_DEADLINE`, `AFT_INSPECT_DIRECT_TIER2_DEADLINE_ROOT`, and `AFT_INSPECT_DIRECT_TIER2_DEADLINE_MS`. Retiring only the Tier-2 budget while leaving the diagnostics budget standing ships deadline-truncated diagnostics under a FRESH label and is the single most likely way to pass this spec while violating it. THE RULE, STATED SO IT DOES NOT COLLIDE WITH GATE-1: no elapsed budget of any kind may CONVERT unfinished work into a returnable result — not FRESH, not Pending, not Stale, not cached-as-current, not provisional, not a verified subset. GATE-1 may still rule a transport-wide or per-phase FAILURE CEILING; such a ceiling is failure policy, not freshness evidence, its only legal expiry effect is whole-call (c) PHASE-FAILED carrying the in-flight `failed_phase`, `failure_reason`, and optional `failure_detail` with no current-result payload, and it is not permission to restore any retired conversion site. Until GATE-1 lands no numeric ceiling and no `transportTimeoutMs` value is committed in a golden. Whether the pending-paths bookkeeping survives for the background lane is an implementation choice; it may NOT be the mechanism by which a non-fresh category becomes part of a returned FRESH payload. Also named: the `ctx.inspect_writer()`-false branch, which today falls back to `tier2_read_cached_readonly`. A reader-only daemon may serve Tier-2 ONLY where stat-verification proves the persisted artifact matches the current tree; if a rebuild is required and this process cannot take the writer lease, the call is (c) PHASE-FAILED, never readonly cached output presented as current.

- **The category set is FIXED and not caller-selectable — "requested category" is defined here (GATE-7a).** `handle_inspect` parses only `sections`, `scope`, and `topK`, then iterates `InspectCategory::active()` unconditionally; `sections` selects DRILL-DOWN DETAIL, not which categories run. So "requested category" means EVERY member of `InspectCategory::active()`, and the whole-call-failure default has a consequence recorded rather than discovered: one unfreshable Tier-2 category fails a call whose todos, metrics, and diagnostics were all verified. No implementation may narrow the obligation by reinterpreting `sections` as a category selector. Whether a real selector is introduced, and whether it changes that blast radius, is GATE-7a; until it lands the all-active reading binds.

- **Tier-1 freshness and non-resolution pre-phase refusals (GATE-7b).** Todos and metrics are FRESH iff each is computed in-call over the stat-verified file list; that in-call computation is their verification ticket. They still dispatch through `manager.submit_category_with_callgraph`, whose non-fresh outcomes may not appear inside a FRESH payload. The unresolved issue is phase attribution and the rendering of non-resolution refusals: `heavy_root_work_allowed()` false (`JobOutcome::Failed` with the heavy-root-work block message), `cache_for_snapshot` / `InspectCache::open_readonly` failure, and `validate_tier2_read_category` rejection. Because the taxonomy is a CLOSED set of three and the closed phase-ID set contains no Tier-1 computation ID, a Tier-1 computation failure or one of those refusals terminates as (c) PHASE-FAILED IN THE PREFLIGHT FORM (empty completed-phase list, no `failed_phase`, no counts, no clean-state claim) unless a recorded GATE-7b amendment supplies phase attribution or a distinct refusal shape.

- **Diagnostics COMPLETENESS, not just per-document verification (GATE-9).** A version/epoch-verified publish proves freshness for a document; it does not prove the server has reported every diagnostics-bearing document in the obligated set. Without a per-server-kind completion oracle, a push-based server that has reported one file yields a zero-count FRESH — reintroducing absence-as-zero. The supported-kind set is derived from the shipped LSP registry plus configuration table, and each acceptance fixture enumerates that derived set in test. Therefore each derived server kind must have a recorded obligated document/workspace set and a mechanically observable completion boundary before FRESH diagnostics ship; elapsed quiet time is not such a boundary unless GATE-1 rules it a failure ceiling rather than freshness evidence. A zero-diagnostics result is FRESH only once every snapshotted applicable server has produced its completion proof over the full obligated set. VACUITY IS CLOSED, so this rule cannot be satisfied by having nothing to prove: an EMPTY applicability snapshot (no applicable server for the root) does NOT satisfy it vacuously — that case is the no-applicable-analyzer terminal ruled by GATE-1, and until GATE-1 lands it may render neither zero diagnostics nor any clean-state claim, exactly as the applicable-server-set constraint states. CONSEQUENCE FOR ACCEPTANCE: a single accepted publish never completes `lsp_quiescence` for a kind whose obligated set has more than one member, and EVERY arm whose terminal is a FRESH diagnostics result carries the GATE-9 label or is split so only its prohibitions run now.

- **Single terminal inspect response (RULED), and the inspect-phase log is a NAMED artifact with a read path.** No deferred partial updates, no progress frames, no new NDJSON push machinery. The terminal wait-stamp is the only agent-visible cost report and lists only phases that actually ran. Phase start/completion/duration/terminal-error are written server-side to the INSPECT-PHASE LOG. That log is NOT `run_tool_call::PhaseTrace`, which is a fixed-field subc dispatch-milestone recorder (`frame_decoded`, `executor_submitted`, `job_admitted`, `translate_done`, `execute_done`, `format_done`, `finalize_done`) with no inspect phase IDs, producer keys, or terminal-error field; building it is REQUIRED WORK, not reuse, and the identical phase-boundary code runs on every transport. BECAUSE FIVE ACCEPTANCE ARMS READ IT, ITS SHAPE IS PINNED HERE RATHER THAN LEFT TO THE IMPLEMENTER: records are per-inspect-call and correlated by request id; each record carries phase id, the producer key where the ID takes one, the category where the ID takes one, start/completion, duration, and terminal error; ordering within a call is guaranteed and is the order the completed-phase list is derived from; records are retained at least for the life of the call plus the assertion window; and the harness reads them through an in-process accessor as well as structured emission, so parity and "no LSP process started" assertions are readable without scraping prose. The log is INTERNAL AND HARNESS-FACING: it is not agent-visible output, so recording it does not create the push channel non_goals bans, and it is not a configuration knob. The earlier alias instructing readers that arms saying "PhaseTrace" mean this log is DELETED, so the wrong recorder cannot be reintroduced by name.

- **RETIRED ON THE INSPECT PATH — an index of the sites named above, adding no new rule.** The `direct_tier2_wait_budget` / `receive_direct_tier2` truncation and its `tier2_run_with_reuse_direct` / `wait_for_tier2_reuse_until` carriers, the `INSPECT_DIAGNOSTICS_DEADLINE` / `collect_scoped_diagnostics_until` truncation, `AFT_INSPECT_DIRECT_TIER2_DEADLINE`, `AFT_INSPECT_DIRECT_TIER2_DEADLINE_ROOT`, and `AFT_INSPECT_DIRECT_TIER2_DEADLINE_MS`, any return of `JobOutcome::Pending` / `Stale` from a blocking inspect, and the readonly-cached Tier-2 fallback except where stat-verified. Where this index and the retirement bullet above appear to differ, the retirement bullet governs.

- **Phase ID vocabulary is closed, shared, and semantically fixed.** `lsp_start`, `lsp_quiescence`, `tier2_rescan`, `callgraph_ready`, `stat_verification` are the ONLY machine-readable phase IDs. PREFLIGHT (the activity window) is everything before any phase: root resolution, applicable-set resolution, missing-executable discovery at resolution, and construction of the applicability snapshot. THE PREFLIGHT FORM (the terminal shape) is: (c) PHASE-FAILED with an empty completed-phase list, no `failed_phase`, no numeric counts, no category summary objects, and no clean-state claim. Preflight failures take the preflight form; so, under the interim GATE-7b rule, do post-preflight refusals and Tier-1 failures that can name no phase — the form is structural and is NOT an assertion that the failure occurred during preflight. `lsp_start` begins only AFTER a successful snapshot and covers process spawn through readiness for a record already in that snapshot — it does NOT cover applicable-set resolution; a spawn-time failure for a snapshotted server is `lsp_start` PHASE-FAILED, not preflight. `lsp_quiescence` covers acceptance of a version/epoch-verified diagnostics snapshot PLUS the server-kind completion oracle (GATE-9), and where the server is rust-analyzer its quiescence signal — a tsserver publish therefore also completes `lsp_quiescence` only once that kind's oracle is satisfied over its whole obligated set, because the ID names the verification step, not the rust-analyzer mechanism. `callgraph_ready` covers cold-build admission (phase start is the start of limiter wait), writer-lease acquisition, callgraph construction, and publication, and appears only where the requested Tier-2 work requires a callgraph. `tier2_rescan` covers Tier-2 computation and publication after any required callgraph is ready, and may complete with no `callgraph_ready` entry where none was required. `stat_verification` covers persisted-artifact identity verification with no rebuild, INCLUDING the gitignore-aware project-file walk that detects added/removed files — that walk is inside this ID's boundary, not a separate ID. DETAIL DIMENSIONS, NOT NEW IDS: producer keys attach to `lsp_start` and `lsp_quiescence` ONLY and to EVERY entry carrying those IDs, including on a single-server root, so a mixed-language failure attributes to a server rather than to the root; the `category` dimension attaches to `callgraph_ready`, `tier2_rescan`, and `stat_verification` ONLY, so a repeated or failed Tier-2 phase attributes to a category rather than to the call. Producer keys may not be attached to the three project-scoped IDs, categories may not be attached to the two LSP IDs, and encoding either dimension by minting a per-server or per-category phase ID is banned. Daemon shutdown names the in-flight phase (with its detail dimension where one applies) where one exists and otherwise takes the preflight form. Completed-phase lists contain only phases whose completion the inspect-phase log recorded. Human wait-stamp prose may paraphrase; the machine field may not. Adding an ID, moving a boundary, or rendering a preflight failure as a phase is a recorded amendment, not an implementation choice.

- **Blocking must not pin drain or executor lanes — including the manager lock, whose lock-released wait seam is NEW WORK.** `handle_inspect` converts from today's Immediate `Response` to the deferred-response seam (`PendingResponses` / `DispatchOutcome::Deferred`). The poll closure is OBSERVE-ONLY: no diagnostics waits, no quiescence waits, no callgraph cold build, no `ColdBuildLimiter::acquire_blocking`, and no writes. LSP start, quiescence wait, and inspect-triggered builds run on dedicated background threads. LOCK DISCIPLINE IS PART OF THE LANE RULE, not an implementation detail: the manager/roots lock serializes LSP mutation only and MUST NOT be held across a diagnostics wait, a quiescence wait, a limiter wait, or a cold build. THE LANE ARM IS ORDERING-BASED, NOT TIMING-BASED: acceptance holds one inspect inside a fixture-controlled wait and requires a second LSP-touching request on another transport to reach its terminal frame BEFORE that wait is released, so no millisecond adverb is used or needed. RECORDED HONESTLY BECAUSE THE OBLIGATION IS NOT SATISFIABLE BY TODAY'S API: `wait_for_file_diagnostics` is an `&mut LspManager` method that blocks on `event_rx.recv_timeout` and mutates diagnostics state while holding the manager, so a background thread using it as-is would stall every other LSP-touching request and falsify the lane-safety arm. Splitting it — establish the wait channel under the lock, await events with the lock RELEASED, re-enter only to apply drained results — is required work, not a call-site rearrangement. The plugin requests a long `transportTimeoutMs` for inspect as bash wait mode does; the numeric budget cannot be committed until GATE-1 fixes the ceiling.
  - SPIKE (open_questions 5): `PendingResponses` exposes only register / poll_ready / is_empty / drain_on_shutdown. There is no cancel-by-request-id seam, so clean per-request abort is NEW work, not reuse of the #188 pattern.
  - SPIKE (shutdown delivery is NEW work, not reuse): `drain_on_shutdown` today is `entries.clear()` — it DROPS every pending response and emits nothing. The taxonomy's no-drop guarantee therefore requires a new emit-before-clear capability with a per-transport flush opportunity. Any wording that reads as reuse of an existing delivery path is wrong and must not be relied on for sizing.
  - SPIKE (seam shape, now GATE-10): `PendingResponse` carries `request_id`, `session_id`, `attach_command`, and a poll closure, and `ResolvedPending` propagates `session_id` / `attach_command`. Inspect has no session or attach-command referent; what it supplies, and whether every `ResolvedPending` consumer tolerates it without misrouting, attaching, or leaking the inspect response, is ruled by GATE-10 and may not be defaulted silently.
  - SPIKE (transports, now GATE-10): only the NDJSON drain tick and the shared polling seam have been read; the subc executor timer, the MCP-rides-subc path, and the main Immediate-versus-Deferred dispatch sites are UNVERIFIED for deferred responses of this duration. All-transports parity is an end-to-end acceptance obligation, not an inference from the shared registry.
  - `handle_inspect` today calls `refresh_status_bar_counts(ctx, &outcomes)` — a WRITE — before building the payload. Under deferral it may not run in the observe-only poll closure. Whether it moves to the background completion path or is removed with the bar-retirement campaign, and in which release order, is GATE-10 — a ruling recorded here, not a decision discharged into a document that is not part of this record.

- **Terminal outcome taxonomy — a CLOSED set of three.** Every blocking inspect ends in exactly one of: (a) FRESH, with wait-stamp; (b) INTERRUPTED (user message / abort), stating which phases completed; (c) PHASE-FAILED, carrying `failed_phase` (from the closed ID set, with its producer key or category detail where the ID takes one), `failure_reason`, and optional `failure_detail`, or taking the PREFLIGHT FORM when no phase had begun or when no phase can legally be named (GATE-7b interim). THREE IS THE WHOLE SET: no `timed_out`, `degraded`, or `partial` without a recorded amendment, because a fourth label is the re-entry route for stale-labelled data. PHASE-FAILED REQUIRES A MECHANICALLY OBSERVABLE FAILURE: crash/exit, explicit failure signal, lease failure, build error, shutdown, or a GATE-1-ruled ceiling or failure signal. Elapsed silence alone is NOT such a signal — absent a GATE-1 ruling, a server that has not yet quiesced leaves the call in-phase until INTERRUPTED or daemon shutdown supplies the terminal outcome, and no implementation may render silence as PHASE-FAILED by picking its own timeout. The remaining wire spelling is unpinned until GATE-1d; downstream may depend on the three-way distinction now and on its encoding only after GATE-1d lands. A FRESH terminal alone carries the wait-stamp; INTERRUPTED and PHASE-FAILED carry only the ordered completed-phase list in the shared entry shape. The completed-phase list carried by (b) and (c) uses the SHARED ENTRY SHAPE defined in the positive-shape constraint, and the preflight form is that list empty. (b) and (c) carry no counts presented as current — TESTABLY: no numeric category counts, no category summary objects, and no details payload readable as a current result — and never reuse the provisional/pending vocabulary as a success path. DAEMON SHUTDOWN MID-WAIT IS BUCKETED: (c) PHASE-FAILED carrying the in-flight `failed_phase`, `failure_reason: daemon_shutdown`, and optional `failure_detail`, or the preflight form when none had begun. Today's clear-only `drain_on_shutdown` behaviour is FORBIDDEN for blocking inspect: shutdown must emit one terminal frame per in-flight inspect before the registry entry is dropped, and providing that emission is required work. Until GATE-1 rules otherwise, ANY requested category that cannot be made fresh fails the whole call as (c); no implementation may emit FRESH covering a subset.

- **Applicable-server set is an explicit, SIDE-EFFECT-FREE resolver output, snapshotted per inspect.** Before background work or any process start begins, inspect resolves and snapshots the applicable records; that snapshot is the call's obligation for its whole life, and applicability discovered later applies to the next inspect. RESOLUTION MAY NOT MUTATE: it may inspect repository language evidence, root markers, resolved configuration, binary availability, and cached spawn classifications, but it MUST NOT spawn, initialize, open a document on, or otherwise mutate an LSP server. The evidence does not establish that `ensure_server_for_file_detailed` satisfies this — it fuses applicability with cached-failure handling and spawning — so splitting resolution from ensure/spawn, or adding an explicit resolver, is REQUIRED WORK; without it snapshot construction can start a server outside any recorded phase and break the preflight/`lsp_start` boundary. A missing executable discovered during side-effect-free resolution is the preflight form with no phase ID; a spawn or initialization failure after snapshot construction is `lsp_start` PHASE-FAILED. THE RECORD SHAPE IS UNSETTLED AND IS NOT LEFT TO THE IMPLEMENTER: the manager keys on `ServerKey` (kind + canonical root), and "configuration identity" as a third compared field is undefined, so snapshot equality and the fixture recording are not implementable until GATE-7c either defines it from the resolved configuration inputs that affect server/root/diagnostics selection or withdraws it; until then the snapshot record is the `ServerKey` pair and fixtures record that. A server is applicable when repository language evidence and resolved project configuration select that kind. Process liveness does NOT affect applicability. `installed`, `configured`, `missing executable`, and `no applicable server for this root` are DISTINCT resolver outcomes and may not be collapsed — an unavailable executable may not be reclassified as inapplicable to make a cold inspect green, and the LSP manager's `failed_spawns` memoization of a prior spawn classification is a missing-executable or spawn-failure outcome, never an inapplicability and never a reason to omit the record. THOSE FOUR ARE PROSE LABELS, NOT A WIRE VOCABULARY: they do not map onto the evidenced `ServerAttemptResult` values (`Ok`, `NoRootMarker`, `BinaryNotInstalled`, `SpawnFailed`) or onto the empty-applicable-set case, so GATE-7d defines the canonical outcome vocabulary and its mapping; until it lands fixtures assert DISTINGUISHABILITY of the four situations, not unruled spellings. FRESH diagnostics require verified completion for every record in the snapshot. ## glossary


- **Retired numeric bar:** the passive status-bar display that can show stale `~` counts or absence-as-zero. Its retirement and replacement belong to the alert-channel-and-bar-retirement campaign, not this one.
- **Agent alert block:** the agent-facing alert-channel rendering owned by the alert-channel-and-bar-retirement campaign. This campaign supplies inspect freshness semantics but does not define that rendering, its length, or its byte goldens.
- **Human fleet line:** the human-facing fleet/status presentation owned by the same alert-and-bar campaign. It is not an inspect terminal payload and must not be used as freshness evidence.
- **Wait-stamp:** the agent-visible cost report: human-readable text plus the ordered completed-phase list. It reports completed work; it is not freshness evidence. A FRESH terminal alone carries the wait-stamp; INTERRUPTED and PHASE-FAILED carry only the ordered completed-phase list in the shared entry shape.
- **Phase entry:** one completed-work record in the wait-stamp, logically `{id, producer?, category?, also_satisfied?: [category,...]}`. `also_satisfied` is present only for a physical work unit that freshened categories beyond its primary category; consumers read absence as an empty list. The same entry shape is carried by all three terminals, so a consumer parses one shape rather than one per outcome.
- **Producer / category attribution:** the two detail dimensions carried by phase entries. `producer` is the stable server identifier and attaches to every `lsp_start` and `lsp_quiescence` entry, including on a single-server root. `category` is the canonical `InspectCategory` wire name and attaches to every `callgraph_ready`, `tier2_rescan`, and `stat_verification` entry. Neither dimension may be encoded by minting a new phase ID; the exact wire spellings are GATE-1d.
- **Closed phase-ID set:** `lsp_start`, `lsp_quiescence`, `tier2_rescan`, `callgraph_ready`, `stat_verification` — the only machine-readable phase IDs. An unknown ID is a failure, and adding an ID or moving an activity across an ID boundary is a recorded amendment rather than an implementation choice. Constraints fix each ID's activity boundary; this entry names the set only.
- **Recorded amendment:** a written change to this spec — in constraints, acceptance, or open_questions — that supersedes a pinned rule, constant, closed set, or gated arm. It is the only legal way to add a phase ID, move an ID boundary, add a fourth taxonomy label, change the fixed 32-release admission schedule or the 5,000 ms warm bound, replace a GATE-7b interim rendering, or drop a gated arm. An implementation choice, a silent scope trim, or a diff that merely stops exercising an arm is not an amendment.
- **Verification ticket:** one of the enumerated mechanical proofs that may license a FRESH claim — document version or epoch match, the per-kind diagnostics completion oracle, stat-verified persisted-artifact identity, rebuild-completed-and-published (generation pointer swap observed), and, for todos and metrics, an in-call computation over the stat-verified file list. Wall-clock age, debounce, quiet time, cached prose, and wait-stamp text are not tickets. A non-fresh Tier-1 outcome takes PHASE-FAILED without entering a FRESH payload.
- **Tier-1 / Tier-2 categories:** "tier" names the freshness path, not a display grouping. Tier-1 categories (todos, metrics) are FRESH iff each is computed in-call over the stat-verified file list; that computation is their verification ticket. Tier-2 categories are the persisted-artifact categories whose freshness is proved either by stat verification of artifact identity against the tree or by rebuild-and-publish after any required callgraph work, with the generation pointer swap observed. Both remain members of `InspectCategory::active()` and are equally required for FRESH until GATE-7a rules otherwise.
- **Whole-call-failure default:** the standing rule, in force until GATE-7a rules otherwise, that any single required category which cannot be mechanically verified fails the ENTIRE call as (c) PHASE-FAILED — even when every other category was verified. FRESH may never cover a verified subset, and an unavailable category may not be encoded inside a FRESH payload.
- **Cold-build limiter / writer lease:** the cold-build limiter admits inspect-triggered callgraph and Tier-2 builds; its permit is awaited on a dedicated background thread with cancellation rechecked before and after acquisition, never in the poll closure. The writer lease authorizes publishing a rebuilt artifact. Lease failure or build error is (c) PHASE-FAILED carrying `failed_phase`, `failure_reason`, optional `failure_detail`, and its category attribution, never a silent stale read and never readonly-cached output presented as current.
- **Preflight / preflight form:** two distinct things, kept separate because one is a time window and the other is a payload shape. PREFLIGHT is the activity window before any phase begins — root resolution, applicable-set resolution, missing-executable discovery at resolution, and applicability-snapshot construction. THE PREFLIGHT FORM is the terminal shape used for those failures: PHASE-FAILED with an empty completed-phase list, no `failed_phase`, no numeric counts, no category summary objects, and no clean-state claim. The form is structural, so post-preflight refusals and Tier-1 failures that can name no phase also take it under the GATE-7b interim rule; taking the form is not a claim that the failure occurred during preflight.
- **Inspect-phase log:** the server-side, per-inspect-call record of phase start, completion, duration, and terminal error, correlated by request id and carrying the producer key or category where the ID takes one. It is the artifact the completed-phase list is derived from and is read by acceptance through an in-process accessor as well as structured emission. It is explicitly NOT `run_tool_call::PhaseTrace`, the fixed-field subc dispatch-milestone recorder; building it is required work.
- **Deferred-response seam:** the `PendingResponses` / `DispatchOutcome::Deferred` registration path `handle_inspect` converts onto, plus the per-transport delivery, flush, and shutdown paths that carry one terminal frame back to the client. The poll closure on this seam is observe-only — no waits, no builds, no writes. The seam has no cancel-by-request-id operation today and its `drain_on_shutdown` clears without emitting, so emit-before-clear delivery, the inspect-shaped envelope, and per-request cancellation are new work under GATE-10 (and GATE-5 for cancellation), not reuse.
- **Admission event:** the harness-visible record emitted by this campaign's NEW cold-build limiter surface when a waiter is admitted, carrying request identity and class (inspect-triggered or maintenance). Deterministic-admission acceptance reads this event rather than log prose; today's limiter emits nothing of the kind. It and the internal per-request class/order state that ticketed ordering would require are internal and harness-facing, not user-visible or globally tunable configuration, and may not be refused as new knobs.
- **Obligated set / completion oracle:** the obligated set is the document or workspace set a snapshotted applicable server kind must have reported before its diagnostics may be called complete; the completion oracle is that kind's mechanically observable boundary proving it did. A single version-valid publish is not an oracle for a multi-member set, and elapsed quiet time is not one at all. An empty applicability snapshot does not satisfy the rule vacuously. Both are ruled per kind by GATE-9, rust-analyzer included, whose quiescence signal is part of its proof rather than a substitute for it.
- **Applicability snapshot / orphan:** the applicability snapshot is the side-effect-free resolver output — recorded as `ServerKey` (canonical root plus server kind) records until GATE-7c rules configuration identity — taken before any process start and binding for the call's whole life. An orphan is a live process group untracked by the child registry or carrying no active idle-reap deadline; a registered server still warming is not an orphan.
- **FRESH / INTERRUPTED / PHASE-FAILED:** the closed terminal taxonomy. FRESH carries mechanically verified current data; INTERRUPTED and PHASE-FAILED carry no category data presented as current, though both carry the ordered completed-phase list in the shared entry shape. A call still in phase is not a fourth terminal outcome.
- **Banned partial-result fields:** the partial-result surface a FRESH response may not carry at any depth (top level, `scanner_state`, `summary`, `details`) — aggregate-side `provisional`, `pending_categories`, `stale_categories`, `incomplete_categories`, `scope_truncated`, `failed_categories`, `complete` in any valuation, the `stale` sentinel in any valuation, and per-category `status: pending|stale|failed`; diagnostics-side `provisional_counts`, `servers_pending`, `servers_not_installed`, `files_without_server`, and any `server_ran: false` payload. The ban is on partial-result FIELDS generally, not on this enumeration alone; the enumeration exists so a named-field assertion cannot go green while an unnamed equivalent ships.
- **Scope / sections:** `scope=` narrows the RESULT set and, until GATE-2 rules a narrowed snapshot, narrows neither server starts nor obligated documents nor freshness work. `sections=` selects drill-down DETAIL and never the set of categories whose freshness is required, which stays `InspectCategory::active()` until GATE-7a rules a real selector.
- **Fenced ground:** the adversarially-audited machinery — lifecycle/epoch handling, quiescence semantics, and artifact publication order — whose predicates, ordering, and visibility timing may not be ALTERED by this campaign, subject only to the non_goals carve-out permitting inspection-started idle-reap deadlines and shutdown escalation through existing child-registry/manager surfaces. Epoch, generation, and publication machinery remain banned. The fence bans alteration, not additive observation: the per-kind obligated-set and completion tracking GATE-9 requires and the inspect-phase log are required work under it. If a kind's oracle cannot be built additively, that is a recorded amendment.
- **Fresh-Tier-2 verdict / delta-engine boundary:** a DECLARED FUTURE INTERFACE minted by the alert-channel-and-bar-retirement campaign; this draft specifies no implementation or acceptance contract for that handoff.
