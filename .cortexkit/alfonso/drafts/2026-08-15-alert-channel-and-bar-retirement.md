## acceptance_sketch


**Retired numeric bar**
- Byte-goldens prove that ordinary responses and `aft_inspect` responses contain no instance of the RETIRED BAR GRAMMAR (the former bracketed AFT health bar in its exact structural form), no `~` staleness marker in any AFT health rendering, no `status_bar` response-envelope field, no 15-call heartbeat, and no plugin-injected duplicate. THE ASSERTION IS GRAMMAR-SHAPED, NOT LETTER-SHAPED: a companion fixture proves that a diagnostic code such as `E0308` inside an alert line, and ordinary prose containing the letters E/W/D/U/C/T, remain legal — a token ban on those letters would contradict the alert contract and must itself redden. The goldens are SCOPED to the agent bar and the alert channel and may not reach into fleet-published bytes while GATE-3 is open.
- Mutation arms restore each retired renderer or emit site independently, and each must redden at least one targeted golden: `formatStatusBar`, `statusBarLine`, `statusBarSuffixForSession`, `statusBarBlockForSession`, `shouldEmitStatusBar`, the `force = true` render on `aft_inspect`, server `refresh_status_bar_counts`, server `should_emit_status_bar` (with `status_bar_last_emitted`), and plugin `captureStatusBar` / `getStatusBar` / `lastStatusBar` on NDJSON and subc.
- REACHABILITY arm (obligation 1, and the reason the omission arm below is not vacuous): a static/instrumented arm asserts that NO caller of `AppContext::status_bar_counts` reaches agent-visible response text or the response envelope on any transport, and that `aft_inspect`'s payload is produced by `build_inspect_payload` rather than from that type. Re-wiring any surviving caller into `response_finalize`, `subc_format`, or the envelope must redden this arm.
- TYPE-SHAPE arm (obligation 2, SERVER side, SURVIVING consumers): unit arms pin that the `todos: tier2.todos.unwrap_or(0)` coercion and the all-or-nothing `(Some, Some, Some) => ... _ => None` aggregate gate no longer produce a silent zero OR a silent whole-aggregate suppression for the consumers that survive — a fixture with exactly one proven category must carry that category and omit the others, which the old gate could not do. A companion arm drives the same fixture twice so the `status_bar_cached` generation cache is exercised, asserting a cache hit reproduces the same omissions rather than resurrecting a zero or the whole-aggregate `None`. With no applicable or installed analyzer, neither the passive channel nor any agent-facing payload may fabricate `E0 W0`; Tier-2-unproven states omit D/U/C. Absence is asserted by optional-field absence, and a plugin fixture proves `parseStatusBarCounts` / `readNumber` do not coerce missing fields to zero on any path reaching a human overlay.
- **[GATE-3]** Fleet-text neutrality arm, written now and branch-neutral: after the type change, the bytes published as `aft_status_segment` are IDENTICAL to the pre-change bytes for the same fixture, including whether a segment publishes at all when only one category is proven, and including any `~` or other legacy token already present in those bytes. Any coercion the segment still needs is asserted to live at the segment's own call site. Changing fleet-visible text or publish conditions before open_questions 3 rules reddens this arm; the arm is rewritten to the ruled behaviour once it lands.
- Fleet-publish survival: an arm asserts `aft_status_segment` is still published to the fleet plane and `holder_owns_status_bar` is still computed after the agent-bar body is removed, reachable under an explicitly named surviving symbol. Deleting `attach_status_bar` wholesale, or deleting the `status_bar_counts` accessor it reads, must redden this arm. **[GATE-3]/[GATE-9]** the segment's own text honesty and the cross-root fleet-publish consequence of retiring `_aft_suppress_status_bar` are unruled; no arm asserts either outcome, and no campaign-wide honesty claim is asserted in CI until they land.
- **[GATE-4]** Pi `StatusBar`/`readStatusBar` and OpenCode `shared/status.ts::readStatusBar` + `tui/sidebar.tsx::collapsedHealthLights` are unruled. One arm is written now and is branch-neutral: neither overlay may render a clean/green state from an absent or unproven value. Survive, delete, or re-bind is decided later; absence-as-clean is forbidden under every branch.

**Alert channel**
- Silent baseline: a session opened against a fixture that already has errors, whose first authoritative observation precedes any this-session edit, renders no alert on that observation and none on a subsequent unrelated call. A companion arm proves the baseline observation SET `rendered` (not merely suppressed the render), by showing an identity present at baseline still does not fire on a later observation.
- Observation-source arm (pins the closed source list and specifically that the channel does not collapse to inspect-only): after a baseline observation, a session mutating-tool edit that introduces an error fires exactly one block with NO intervening `aft_inspect` call, driven by the post-edit verified diagnostics wait alone. A second variant drives source (iii) — a verified publish accepted for a root whose server is already live and quiescent — and also fires. A build in which only an explicit inspect can produce an observation reddens this arm. A negative variant proves a warming (pre-quiescence) report and a passive count read are NOT observations, and that the post-edit wait started no server on a cold root.
- PARTITIONING arms (a root-wide `live` set is a defect, asserted directly): on a two-server root, (i) an observation that accepts a verified snapshot from server A only updates A's partition and leaves B's `live` and `rendered` untouched — a build that substitutes a root-wide `live` will falsely mark B's identities `gone`, prune them from `rendered`, and re-page them on B's next publish, which this arm must catch; (ii) a post-edit wait with server B pending, exited, timed-out, or warming does not clear, prune, or otherwise mutate B's partition; (iii) a server first observed later does NOT flood its pre-existing diagnostics merely because another server baselined earlier — its own first observation is its own silent baseline; (iv) a multi-server observation finalizes as ONE ATOMIC BATCH containing exactly the producer partitions whose complete version/epoch-verified snapshots were accepted. Pending, exited, timed-out, or warming producers are omitted from that batch and left untouched; no intermediate state of the terminal batch is observable from concurrent finalization.
- RECOMPUTED-NOT-QUEUED arm: an identity published and then REMOVED by a later authoritative observation before any eligible agent-visible response is finalized is NOT rendered, is NOT added to `rendered`, and — having been silently pruned — fires normally if it returns later. A queued-candidate implementation that renders an already-resolved diagnostic reddens this arm. At finalization, the fixture supplies a DISPATCH ROOT for the response and asserts the deliverable set is the union of `live − rendered` only across that session-and-dispatch-root's partitions; a coalesced block may span two producers in that root but cannot borrow or consume another root's state.
- First-observation branch arm, exactly one of two, never both green: DEFAULT branch — a fixture that edits a diagnostics-bearing file and then takes its FIRST authoritative observation of that partition renders NO alert for the newly introduced identity, which is in `rendered`, and the error is reachable only via `aft_inspect` (the accepted residual, asserted rather than discovered); **[GATE-10]** KEEP-STORE branch — the same fixture renders exactly one block with the your-edit clause, and every non-attributable identity present in that partition is still baselined. The fixture names which branch it encodes; a branch flip without a recorded ruling is a contract violation.
- Silent prune and re-entry: an identity that leaves `live` and later returns fires again exactly once; a mutation that keeps pruned identities in `rendered` must redden it. Disappearance or recovery alone renders nothing.
- Identity normalizer: a unit arm runs the single named normalization function against a fixed table (first line, trim, whitespace-run collapse, NFC — and nothing else). Table entries prove that path rewriting, numeric elision, and quote folding do NOT occur; adding any of them must redden.
- **[GATE-10]** Attribution, three arms, mutation-proofed both directions. Every arm expecting a block after an edit FIRST performs an authoritative observation of the SAME PARTITION that establishes the baseline (asserted in the fixture, including that `baseline_established` was set), THEN applies the causative mutation. (i) a session mutating-tool edit introducing an error renders exactly one `<system-reminder>` block on the FIRST AGENT-VISIBLE response after that diagnostic is published — not necessarily the next one after the edit — with file:line, first message, and the your-edit clause; (ii) an external/bash-mediated or watcher-only mutation of the same file renders the same block with NEUTRAL wording and no clause; (iii) an unrelated call with no session-new error renders no block at all. Arms (i) and (ii) presuppose a session-scoped last-mutating-tool + document-version/epoch store that is NOT evidenced today. If the spike finds no store and the owner does not build one, (i) and (ii) are REWRITTEN to the neutral-only form and the your-edit clause is deleted from copy and goldens; they may not be left green by asserting on document version alone.
- **[GATE-10]** Analyzer-lag arm: after baseline, a diagnostic published three eligible tool calls after the causative edit still alerts and still attributes (version >= mutation version). Forcing a longer lag must not change the rendered clause or select a later ride. Withdrawn with the clause under the drop branch; the alert-still-fires half survives either way.
- Coalescing arm: two or more new identities accumulated between renders produce exactly ONE block, ordered newest-first by the session-global observation ordinal in which each entered `live` (ordinals span producer partitions, so a two-server coalesced block still has one total order), with same-observation ties broken by the canonical identity tuple (asserted by a fixture in which two identities enter in the SAME observation, so a non-deterministic order reddens the byte-golden), with the exact `(+N more)` count of UNSHOWN identities, within the exact 3-line cap (at most 2 alert lines plus the `(+N more)` line, excluding reminder tags). Assert block count == 1 and that the next unchanged response is silent. Every identity represented by the finalized block, INCLUDING those counted only by `(+N more)`, is asserted to be in its owning partition's `rendered` afterwards.
- Truncation arm: a single over-long diagnostic yields exactly one block, one line, ellipsis-truncated at the fixed maximum line length, never wrapped. **[GATE-6]** the constant, the unit it is measured in, and the ellipsis token are unruled (open_questions 6); the arm asserts the truncation PROPERTY now and pins the number, unit, and token in a golden once chosen.
- Re-emission arm: an already-rendered identity does not re-fire; reintroducing the 15-call heartbeat or the force-on-inspect render must redden a golden. A companion arm proves `aft_inspect` CARRIES a pending block like any other agent-visible response while never forcing one.
- Exclusion arm: internal/transport commands neither carry nor consume a pending alert — a pending block survives an excluded call and rides the next agent-visible response. The excluded set is asserted against a CLOSED list snapshotted verbatim into the fixture from today's attach exclusion list, not against whatever the code excludes at run time: an internal command outside the snapshot that neither carries nor consumes reddens the arm, so adding a command forces a recorded placement decision instead of drifting silently.
- Isolation arms, both directions: no cross-session and no cross-root bleed; alert state does not persist beyond the session (a new session against an unchanged tree re-establishes a silent baseline rather than firing). If a durable digest baseline store exists (open_questions 7b), an arm proves the alert channel does not read it.
- Cold-root silence arm: no analyzer running for the root plus an edit that breaks the build ⇒ no block, and specifically no rendered health-count token (`E0`, `W0`, or any other category token in the retired bar grammar) and no clean-state claim anywhere in the response. THE BAN IS GRAMMAR-SHAPED, consistent with the retired-bar goldens above: a diagnostic code beginning `E0` remains legal wherever an alert legitimately renders, so the arm keys on the count-token grammar rather than on the letter pair. The passive path is asserted to have started no server.
- Host-uniformity arm: byte-golden proves identical rendered block text on NDJSON, subc, and MCP text-only, with no host-side reformatting, no UI-metadata lane, and no second injection path, and never more than one reminder block on one response. A companion golden with the fleet line present on the same response proves the block renders byte-identical to its fleet-absent form and that the response contains no RETIRED health-count token shapes other than a fleet line that already contains them; the legal `(+N more)` suffix remains an alert-identity count — this is the testable meaning of COMPOSE.
- Trigger-set arm: a Tier-2 count delta or todo change with no new error diagnostic renders no block; the same delta is visible via `aft_inspect`. Warnings, info, and hints likewise never page this channel.
- Alert/aggregate split: no project-wide counts in the alert channel; `aft_inspect` remains the aggregate surface with its category set and `sections` contract unchanged.

**Delta engine, two consumers**
- Snapshot isolation, asserted in BOTH directions on the same fixture, across ALL THREE alert fields, and on EVERY producer partition: a `health.digest` call for a (session, root) never reads or writes `live`, `rendered`, or `baseline_established` in any partition — a later agent-visible response still fires the block for that identity, a digest call cannot itself establish a silent baseline, and a digest call cannot advance `live` so as to flood a later observation — and rendering an alert block never mutates any digest anchor. A shared mutable snapshot must redden both arms.

**`health.digest` (AFT-side slice only)**
- Not-an-agent-tool arm: no agent-facing tool definition is registered, the op never appears in tool-response text on any transport, and a digest call neither carries nor consumes a pending alert block. The op is reached by NAME (`health.digest`); the fixture keys on that name so a rename reddens rather than silently re-binding.
- Passive-bound arm: a digest call against a cold root starts no server, never blocks on quiescence, never triggers a cold build, and OMITS diagnostics rather than reporting zero or `~`.
- **[GATE-7] Pre-gate freshness-only arms:** a digest value is admitted only with its category's freshness ticket and a conceptual `since` baseline, but no arm calls any value new, changed, resolved, or a delta relative to `since`. The arm exercises reusable identity, normalization, verification-or-omit, passive behavior, and consumer isolation only. It asserts FRESH VALUES, not interval membership. A value without its ticket is omitted; it is never fabricated as zero, `~`, or an empty delta.
- **[GATE-7] Post-gate interval arms:** after Gate 7 rules `since`, baseline, and interval membership, each category arm proves BOTH its freshness ticket and membership in the ruled interval: current error diagnostics use an already-live version/epoch-verified snapshot; Tier-2 values use stat-verified artifact identity; TODO values use that same artifact; watcher values use accepted journal events with their accepting stat identity; and resolved diagnostics use the ruled durable baseline. Until then, no category is represented as a delta, including resolved diagnostics.
- Structured-fields arm: the reply carries no pre-rendered prose, no retired bar grammar, and no `~` marker. Ticketed numeric current values are permitted where a number is the datum, but a pre-gate fixture asserts only freshness and omits any delta label or interval claim; an assertion banning integers outright would contradict the structured-value contract and must itself redden.
- **[GATE-7] Wider-trigger arm:** after Gate 7, a root with a live server, stat-verified Tier-2 data, TODO data, and a watcher summary proves that these digest categories are representable only when each is both fresh and in the ruled interval. They never page the alert channel.
- **[GATE-7]/[GATE-8]** No wire schema, field name, `since` type/boundary, ordering, retention, restart-survival, or exposure/authorization behaviour is frozen in a golden. Conceptual `{root, since}` freezes neither encoding, field names, `since` type, nor root cardinality. No pre-gate fixture depends on an interval anchor; "delta-engine reuse" remains identity, normalization, verification-or-omit, and consumer-scoped isolation, never reuse of the session alert snapshot as a `since` baseline.

**Release-boundary copy**
- The alert-channel explanation is asserted to land on the ONE release boundary that carries the blocking-fresh inspect tool-description changes; `health.digest` introduces no agent tool-description change.

**Observation logging (mechanism in scope, outcome out)**
- TWO record kinds are constructed SERVER-SIDE, but durable writes are scoped NOW to OpenCode-hosted sinks. Other harnesses receive the same alert bytes and record schema construction, while a production sink, retention, write-failure behavior, and query surface for them are declared future behind **[GATE-11]**. (1) ALERT-RENDERED is written at finalization once PER IDENTITY represented by the finalized block, including identities counted only by `(+N more)`, carrying a shared **block id**, session id, dispatch root, producer key, tool-response id, diagnostic identity fingerprint, file:line, severity/code, attributed-vs-neutral form, SHOWN-vs-COUNTED-ONLY flag, the session-global `agent_visible_response_ordinal`, and lifecycle episode id. All rows for one block share its block id; the identity fingerprint plus lifecycle episode id is the per-row key. (2) DISAPPEARANCE is written when a previously rendered identity leaves `live` at an authoritative observation of its partition, carrying the same lifecycle episode id, session, root, producer key, observation ordinal, and the same session-global `agent_visible_response_ordinal`. A kind-(1) arm proves the complete row set for a rendered alert in an OpenCode-hosted sink, including one row for every counted-only identity in a coalesced fixture; a per-block-only implementation or omission of counted-only rows must redden it. A separate arm asserts kind (2) is measurement-only — it never renders and never pages the alert channel.
- Lifecycle arm: when an identity first appears in an authoritative observation, its lifecycle episode id is minted and stored in session delta state. Its episode closes on disappearance; if the same identity re-enters, a NEW id is minted. A repeated disappearance → re-entry → disappearance fixture renders both episodes, inserts exactly two non-rendering agent-visible responses between the first render and the second disappearance, and proves the two disappearance rows join only their matching render row. The fixture also proves that both record kinds use the one session-global agent-visible-response ordinal domain, which increments for every agent-visible finalization whether or not it carries a block.
- Record-source isolation arm: a `health.digest` call writes NO record of either kind, even when its structured reply contains ticketed current values. Kind (1) writes are confined to alert finalization and kind (2) writes are confined to authoritative observations that remove a previously rendered identity from its producer partition.
- The committed offline query computes "alert rendered → diagnostic resolved within N turns" with N fixed at 5 turns, joining kinds (1) and (2) on producer key plus lifecycle episode id, WITHOUT parsing rendered prose. Its fixture includes both SHOWN and COUNTED-ONLY identities and the known non-rendering response gap, so it proves both populations are joinable in the shared ordinal domain. Dropping counted-only kind-(1) rows, recording only one row per block, or joining a re-entry to its former episode reddens the query arm. A build that omits kind (2) must instead name an EXISTING durable diagnostics-transition source and prove by fixture that it joins on producer and lifecycle episode id; an arm asserts that "a join key alone" does not satisfy this, by showing the query cannot be computed from kind-(1) records only. The `opencode.db` instance is ONE consumer of the records for the OpenCode measurement window, not their home.
- CI asserts the record SCHEMAS, per-identity granularity, the SHOWN-vs-COUNTED-ONLY distinction, episode separation, and that the query runs against the fixture; it does NOT assert the efficacy result. LEBENCH-style before/after evidence stays out of CI. **[GATE-11]** the non-OpenCode sink, retention, write-failure behavior, and query surface are unruled; no arm freezes them. ASSUMPTION ON RECORD: the campaign premise — event-shaped reminders are acted on where numeric trailers are not, and wake-from-dark is when orientation data is actionable — is falsified by no test here; owner, baseline dataset, measurement window, success metric, the sink for non-OpenCode sessions, and the response to a null result (revert the alert channel, revert the digest, or keep both on the honesty argument alone) must be named before ship.


## constraints


- **The delta engine is ONE component with TWO consumers, and what is shared is bounded.** SHARED AND BUILDABLE NOW: canonical error-diagnostic identity, the named normalization function, the verification-or-omit filter, and consumer-scoped snapshot discipline. NOT SHARED AND NOT YET DEFINED: a durable digest `since` baseline, its interval semantics, retention, restart behaviour, or any delta classification. Consumer A's alert state is session-scoped and non-persistent, so it cannot back a digest `since` anchor older than the session. Consumer A is the AGENT ALERT BLOCK (in-context, session-scoped, errors-only, new-only). Consumer B is `health.digest` (management-surface; its wider trigger set is a Gate-7 destination). A digest value carries both a category freshness ticket and the conceptual `since` baseline, but until Gate 7 defines that baseline and membership it is a FRESH VALUE, never a representation of a new, resolved, changed, or delta value. "Delta-engine reuse" therefore names identity + normalization + verification-or-omit + isolation, never an implemented since-anchored diff. SNAPSHOT OWNERSHIP IS CONSUMER-SCOPED AND MUST NOT BLEED: a `health.digest` call never reads or writes Consumer A's `live`, `rendered`, or `baseline_established`, and rendering an alert block never mutates any digest anchor. A shared mutable snapshot is a defect, not an optimization.

- **Alert delivery is host-uniform and server-rendered (RULED).** AFT already owns final response text on NDJSON, subc, and MCP (`response_finalize` / `subc_format`); the alert block is appended there as a `<system-reminder>`-tagged block, riding the same convention as bash completion reminders. No UI-metadata lane, no per-host formatter, no plugin-side renderer — Pi, OpenCode, and MCP text-only receive identical bytes. HARD CAP IS EXACT, NOT APPROXIMATE: at most 3 rendered lines excluding the reminder tags — at most 2 alert lines, plus, when more identities are pending, a third line consisting solely of `(+N more)` where N is the count of UNSHOWN identities. ORDERING IS TOTAL AND DETERMINISTIC: newest-first by the authoritative-observation ordinal in which the identity entered `live` this session (ordinals are session-global across producer partitions, so a coalesced block from two servers still has one total order); identities entering in the SAME observation are ordered by the canonical identity tuple (canonical root-relative file, range start, range end, severity, source/server, code-presence then code, normalized first message). Host-uniform byte-goldens depend on this tie-break. Each alert line is truncated to a fixed maximum length (a release-blocking product constant, **[GATE-6]** open_questions 6) with an ellipsis rather than wrapping; a single over-long diagnostic still yields exactly one block. Never multiple reminder blocks on one response.
  DELIVERY IS RECOMPUTED, NOT QUEUED. There is no persistent candidate queue. At finalization, the DISPATCH ROOT of the response being finalized is the sole canonical root that supplies and consumes alert state; alerts never attach to another root's response. The deliverable set is recomputed only as the union, across that session-and-dispatch-root's producer partitions, of `live − rendered`. Consequence, stated so it cannot be discovered later: an identity published and then REMOVED by a later authoritative observation before any eligible response is finalized is NOT rendered, is NOT added to `rendered`, and — having been silently pruned — becomes deliverable again if it returns. A queued-event implementation that renders an already-resolved diagnostic violates this rule. Once `baseline_established` holds for a partition, publication of a new identity makes it deliverable and the next AGENT-VISIBLE response after that publication carries it only if it is still in `live` at finalization, so analyzer lag never selects a later ride. Publication that IS the first authoritative observation of its partition does not make it deliverable under the default branch below. Internal/transport commands neither carry nor consume a pending alert; the exclusion set is snapshotted verbatim from today's attach exclusion list into a CLOSED fixture list rather than referenced as "whatever the code excludes", so adding an internal command reddens until it is explicitly placed. `aft_inspect` never FORCES a block, but it carries a deliverable block like any other agent-visible response. All identities represented by a finalized block, INCLUDING those counted only by `(+N more)`, are added to their owning partition's `rendered`.

- **Alert predicate (per session × root, PARTITIONED BY DIAGNOSTICS PRODUCER, explicit state machine).** Candidates are ERROR-severity diagnostics only; warnings, info, hints, Tier-2 D/U/C, and todos never page this channel. Diagnostic identity is the tuple (canonical root-relative file, range, severity, source/server, code when present, normalized first message). NORMALIZATION IS DEFINED as: take the first line of the message, trim, collapse internal whitespace runs to a single space, apply NFC — and nothing else. No path rewriting, no numeric elision, no quote folding. The normalizer is a single named function asserted by unit test against a fixed table. Rendered location is the file plus the start line of `range`.
  An AUTHORITATIVE OBSERVATION is server-side acceptance of a version/epoch-verified diagnostics snapshot (rust-analyzer: after quiescence) for a root that already has a live server, or that this inspect just started and verified. Unverified warming reports and passive count reads are NOT observations; the passive path never starts a server to obtain one. A `health.digest` call is NEVER an observation for this machine.
  OBSERVATION SOURCES ARE A CLOSED SET, so the firing condition is testable and cannot silently collapse to inspect-only: (i) the existing post-edit diagnostics wait on this session's mutating tools, for a root whose applicable server was ALREADY live — the wait never starts one, so a cold root stays silent — whose outcome type already carries only version/epoch-verified entries; (ii) diagnostics accepted by a blocking `aft_inspect` under the freshness rules above; (iii) a version/epoch-verified publish accepted into the continuously-drained store for a root whose server is ALREADY live and, for rust-analyzer, quiescent. Nothing else — no timer, no heartbeat, no passive count read, no warming report. Source (i) is what makes an agent edit that breaks the build page WITHOUT an intervening `aft_inspect`; a build in which only (ii) can fire is a defect against this list.
  STATE IS PARTITIONED. Per `(session, canonical root, producer key)` — where the producer key is the same stable server identity used by diagnostics acceptance — the engine holds `baseline_established`, `live` (identities in that producer's last authoritative observation), and `rendered` (identities acknowledged this session for that producer). For every identity, a lifecycle episode id is minted when it first appears in an authoritative observation and is stored in this session delta state. A ROOT-WIDE `live` SET IS A DEFECT: source (iii) delivers one producer's snapshot, and source (i)/(ii) may complete for some producers while another is pending or exited, so a root-wide substitution would falsely mark unobserved producers' identities `gone`, prune them from `rendered`, and re-page unchanged diagnostics on the next publish.
  An observation updates ONLY the partitions for which a complete version/epoch-verified snapshot was accepted. A multi-server observation applies ONE ATOMIC terminal batch containing exactly those accepted producer partitions. Pending, exited, timed-out, or warming producers are omitted from that batch and left unchanged; no partial state of the terminal batch is observable from concurrent finalization.
  FIRST authoritative observation OF A PARTITION — DEFAULT branch, and the ONLY branch if open_questions 10 drops the mutation store: set that partition's `live` and `rendered` to its current error identities, set `baseline_established`, render nothing. This is the silent baseline and the ONE case where `rendered` advances without a block; it is what prevents a pre-existing-diagnostic flood. Because it is per-partition, a server first observed later does NOT flood its pre-existing diagnostics merely because another server baselined earlier. ACCEPTED RESIDUAL, recorded rather than discovered later: a session whose first edit precedes any observation of the relevant partition has its own new error absorbed by that baseline and is not alerted; that error is reachable only via `aft_inspect`. Attribution and "edit introduces error" fixtures MUST therefore perform a prior authoritative observation of the same partition before the causative edit and must assert in the fixture that it ran and set `baseline_established`.
  FIRST authoritative observation — GATE-10 KEEP-STORE branch only: within the partition being baselined, identities whose file's last known mutation is owned by THIS session's mutating tools AND whose diagnostic version/epoch >= that mutation are withheld from `rendered` and are deliverable immediately; every other current identity in that partition is baselined. This is the only branch on which a first observation may render a block, and it exists only if the mutation-ownership store is built.
  LATER observations of a partition: let `gone = previous live − current`; close the lifecycle episode of every identity in `gone`; set `live := current`; set `rendered := rendered − gone` (silent prune); and mint a NEW lifecycle episode id for each returning or otherwise newly observed identity. Disappearance or recovery alone renders nothing. An identity that left `live` and later returns is absent from `rendered`, is deliverable again, and never joins its former episode. No heartbeat re-emit, no force render on `aft_inspect`, no cross-session or cross-root bleed, no persistence beyond the session.

- **Attribution is version-anchored, not time-anchored (RULED).** The attribution clause attaches iff the file's last known mutation is owned by THIS session's mutating tools AND the diagnostic's document version >= that mutation's version; where a server exposes no document version, the epoch is used instead. Analyzer lag is therefore irrelevant. If neither anchor can be established, or if any other actor (worktree merge, bash-mediated git, another session, watcher-observed external edit) owns the last mutation, the clause drops and the alert renders neutrally (`new error in parser.rs:141 (E0308 ...)`). Accepted residual: same-session edit followed by an unobserved external edit to the same file at an indistinguishable version keeps the clause wrongly — content identical, only the clause differs. No wall-clock window exists anywhere in this design.
  - SPIKE (open_questions 10): session-owned mutation tracking on the edit path is NOT evidenced — the evidence shows LSP document versions and per-file post-edit diagnostics only. Do not implement the clause against document versions alone. If the store is absent, building it is in-campaign work, or the owner drops the clause and the attribution acceptance arms are rewritten before implementation. Dropping the store also LOCKS first-observation to the DEFAULT silent-baseline branch above; it does not leave first-observation behaviour unruled.

- **`health.digest` (AFT-side slice), with a verification ticket per category.** A management-surface operation, conceptually `{root, since}`, discovered by op name and consumed by the wake composer as an ordinary client — symmetric to prefrontal's `status.line`. This conceptual notation freezes neither encoding, field names, `since` type, nor root cardinality. The op NAME is this spec's stable downstream identifier: fixtures, discovery-by-name, and every cross-section reference key on `health.digest`; renaming it is a recorded amendment under open_questions 7(a), not a drafting liberty. It is NOT an agent tool: no agent-facing tool definition, no in-context rendering, no appearance in any tool-response text on any transport, and it neither carries nor consumes a pending alert block. It never starts a server, never blocks on quiescence, and never triggers a cold build.
  THE SAME VERIFICATION-OR-OMIT LAW BINDS EVERY `health.digest` REPLY. Every value carries its category freshness ticket and the conceptual `since` baseline. **[GATE-7]** Until `since`, the durable baseline, and interval membership are ruled, the reply may assert FRESH CURRENT VALUES only; it may not describe diagnostics, Tier-2 values, TODOs, or watcher events as new, resolved, changed, or delta relative to `since`. ## glossary

- **Retired numeric bar:** the former agent-facing bracketed AFT health rendering and its E/W/D/U/C/T count-token grammar, response-envelope field, heartbeat, plugin renderers, and plugin caches. This does not name the fleet line or the legal `(+N more)` alert-identity suffix.
- **Agent alert block:** the server-rendered, `<system-reminder>`-tagged, errors-only block attached at finalization to one agent-visible response. It is a session-scoped consumer of the delta engine and is never a count aggregate.
- **Dispatch root:** the canonical root of the response currently being finalized. It is the only root whose partitioned alert state can supply or consume that response's `live − rendered` set.
- **Producer partition:** state keyed by `(session, canonical root, producer key)`. It owns `baseline_established`, `live`, `rendered`, and each identity's lifecycle episode state.
- **Authoritative observation:** acceptance of a complete version/epoch-verified diagnostics snapshot for one producer partition. Warming reports, passive count reads, and digest calls are not observations.
- **Lifecycle episode id:** a session-delta-state identifier minted when an identity first appears in an authoritative observation, closed when it disappears, and replaced by a new id if the identity re-enters.
- **Freshness ticket:** category-specific evidence that a current digest value is trustworthy. It is not interval membership and never, by itself, proves that a value is new, resolved, changed, or a delta.
- **Conceptual `{root, since}`:** the logical digest input pair. It does not freeze wire encoding, field names, `since` type, root cardinality, ordering, retention, or exposure.
- **OpenCode-hosted sink:** the only durable observation-record sink in scope now. Non-OpenCode durable sinks are future work under Gate 11.

## design

The design has two isolated consumers. The alert consumer observes verified error diagnostics per producer partition, silently baselines each partition's first observation, silently prunes a disappeared identity, and recomputes delivery from the dispatch root at finalization. It emits at most one ordered reminder block per eligible response. The alert consumer has no queue, no heartbeat, no force-on-inspect path, no cross-root borrowing, and no persistent state beyond the session.

The digest consumer is a management-surface operation rather than an agent tool. It reuses canonical identity, normalization, verification-or-omit, and consumer isolation, but it owns its own conceptual `since` baseline. Before Gate 7, it can expose ticketed fresh current values without asserting an interval delta. Once Gate 7 rules interval semantics, every delta category must prove both a ticket and membership in the ruled interval. Digest reads never establish an alert baseline, advance alert `live`, consume a pending alert, or write an observation record.

The retired bar is removed from agent-visible responses without deleting the fenced fleet lane. `attach_status_bar` may be edited now to remove the agent-envelope insertion and preserve the current fleet publish. Gate 9 decides only the env-specific cross-root fleet-suppression behavior. The fleet compose golden bans retired health-count token shapes outside the fleet line while preserving `(+N more)` as a count of unshown alert identities.

Observation records are constructed at the server-side alert events. Each finalized alert block produces one ALERT-RENDERED record per represented identity; a disappearance produces a DISAPPEARANCE record only when the identity had been rendered. Both records use the same session-global agent-visible-response ordinal and the lifecycle episode id. The five-turn query joins on producer key plus lifecycle episode id, never rendered prose. Durable writes are limited to OpenCode-hosted sinks until Gate 11 names the other harnesses' sink and failure behavior.

## interfaces

- **Alert finalization interface:** finalization receives or derives exactly one dispatch root. It queries only that root's producer partitions, appends at most one server-rendered reminder block, marks every represented identity rendered in its owner partition, and emits per-identity record events to the logging interface. No other slice edits `response_finalize.rs`.
- **Observation-update interface:** an accepted snapshot is supplied as `(session, canonical root, producer key, verified identities)`. A multi-server terminal update is one atomic batch containing exactly accepted producers; pending, exited, timed-out, and warming producers are absent and unchanged. The update returns lifecycle opens/closes and current state for finalization without exposing a root-wide `live` set.
- **Digest interface:** `health.digest` is addressed by name and has conceptual inputs `{root, since}`. Before Gate 7, its logical output is ticketed fresh current values or omitted fields; it has no frozen wire schema or delta vocabulary. After Gate 7, the interface must prove ticket plus ruled interval membership for every delta-bearing category. Gate 8 owns registration, authorization, and transport exposure.
- **Observation-record interface:** an alert event supplies block id, dispatch root, producer key, identity fingerprint, lifecycle episode id, shown/count-only status, and `agent_visible_response_ordinal`; a disappearance supplies the same episode and ordinal domain. The OpenCode-hosted sink accepts these schemas now. A future harness sink is not implied by construction of the event.
- **Fleet-composition interface:** retirement code preserves `aft_status_segment` publication and `holder_owns_status_bar` through a named surviving call site. Fleet output remains byte-neutral until Gate 3; the compose golden observes it but does not redefine it.

## acceptance_criteria

- Agent-visible ordinary and inspect responses contain none of the retired bar grammar, `status_bar` envelope field, heartbeat, stale marker, or duplicate plugin renderer. The assertions are grammar-shaped: `E0308`, ordinary prose containing E/W/D/U/C/T, and the legal `(+N more)` alert-identity suffix remain valid.
- The alert engine updates only accepted producer partitions, gives every first partition observation a silent baseline, silently prunes disappearance, assigns a new lifecycle episode on re-entry, and at finalization consumes only the dispatch root's `live − rendered`. A response rooted at A cannot render or consume state from B.
- Alert delivery is byte-identical and exactly-once across the actual invocation surfaces. Per-transport terminal-delivery arms invoke the real binary over NDJSON, subc, and MCP. They verify the same reminder bytes, one terminal attachment, no host formatter, and no duplicate injection path.
- Before Gate 7, digest tests prove ticketed FRESH VALUES, omit-not-zero behavior, passive no-server-start behavior, and alert/digest isolation. They make no new/resolved/changed/delta claim. After Gate 7, each digest category test proves both its freshness ticket and ruled interval membership.
- Observation tests prove per-identity rows for shown and counted-only identities, a repeated disappearance → re-entry → disappearance sequence with non-rendering agent-visible responses between episodes, distinct episode ids, and a correct five-turn join in the shared ordinal domain. Durable-write acceptance is limited to OpenCode-hosted sinks; other harness durability is gated by Gate 11.
- The slice partitioning section's file fences remain non-overlapping. In particular, the alert engine alone owns `crates/aft/src/response_finalize.rs`; passive retirement, digest, observation logging, and fleet compose-golden slices integrate through their named interfaces.

## open_assumptions

- The attention-model claim — agents act on event-shaped reminders more readily than passive numeric trailers and find wake orientation actionable — is rationale, not a tested acceptance property. Gate 11 must name the owner, baseline data, measurement window, success metric, and null-result action before ship.
- Dark-start timestamp, structured fields with holder-composed rendering, and per-root digest calls are owner leans, not a settled digest wire contract. Gate 7 decides their contract consequences.
- A suitable session-owned mutation store may not exist. Gate 10 must either build it or remove the attribution clause and lock first observation to the default silent baseline.
- The durable sink, retention, write-failure behavior, and query surface outside OpenCode-hosted sinks are deliberately unassumed. No cross-harness durability claim is made before Gate 11.
